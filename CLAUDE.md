# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local platform for grading Terminal-Bench-style task submissions. A user uploads a task zip (`task.toml`, `instruction.md`, `environment/Dockerfile`, `solution/solve.sh`, `tests/test.sh`) and runs it through stages against real Docker containers: Build → Oracle → Nop → Sufficiency → Agent Trials, plus the advisory stages Leakage Scan and Review Report.

Two apps live in one repo: a FastAPI backend in `backend/` and a TanStack Start (React 19, Vite, Tailwind v4, shadcn/ui) frontend at the repo root.

## Lovable constraints (from AGENTS.md)

The repo is connected to Lovable. **Never force-push, and never rebase, amend or squash commits that are already pushed.** Commits pushed to the connected branch (`main`) sync into the Lovable editor, so keep that branch working.

## Commands

```sh
# Postgres (localhost:5433, persistent volume taskeval-pg-data)
docker compose up -d

# Backend (from backend/). Needs Docker running, the harbor CLI on PATH, and one provider key in .env
cp .env.example .env
uv sync
uv run uvicorn app.main:app --reload --reload-dir app --port 8001

# Frontend (from repo root). The client defaults to :8000, so set the URL explicitly
bun install
VITE_API_BASE_URL=http://localhost:8001 bun run dev
bun run lint        # eslint
bun run format      # prettier
bun run build
```

There's no test suite and no migrations. Tables come from `Base.metadata.create_all` at startup, so a schema change to an existing table means wiping the DB (`docker compose down -v`). Runtime state lives under `backend/storage/`, which is gitignored and safe to delete.

## Backend architecture

**Request → background task flow.** `routers/submissions.py` exposes `POST /submissions/{id}/<stage>`. Each endpoint marks the row `pending` and hands a coroutine from `services/task_runner.py` to `workers/task_queue.submit(key, coro)`. The queue is in-process asyncio only: resubmitting the same `"{id}:{stage}"` key cancels the running task and restarts it. Blocking Docker calls run through `asyncio.to_thread`. Cancelling a Harbor-backed stage sends SIGINT to the `harbor` process so it removes its containers. On startup, `reset_stuck_rows()` marks any leftover `pending`/`running` rows as failed, and `docker_orchestrator.reap_orphans()` removes containers labelled `taskeval.submission_id`.

**Data model.** `Submission` holds build state, the image tags, the cached parsed `task.toml` (`task_config_json`, a `TaskConfig` model), and `task_checksum` (see below). Every other stage result is a `Run` row keyed by `(submission_id, kind, run_index)`. `kind` is one of `oracle`, `oracle_stress`, `nop`, `agent` (one row per trial), `sufficiency`, `leakage_scan`, `review_report`, `failure_analysis`, `cheat_trial` (one row per trial), `rubric_check`, `static_checks`, `tb_static_checks`, `ai_detection`, `variant_probe`, `weak_probe`, `edge_cases`, `reviewer_decision`, `answer_exposure`, `image_inventory` or `fresh_build`. `services/submission_service.to_schema` turns runs into the per-stage API shape. For example, it inverts Nop's status, because reward 0 counts as a pass there. `schemas.py` and the types in `src/lib/api.ts` must stay in sync by hand.

**One frozen task version per run set.** Every Oracle/Nop/Agent Trials `Run` row also stores the `task_checksum` Harbor's own `result.json` reports (its dirhash of the exact task directory that trial ran against). `task_runner._record_checksum` writes it onto the `Run` and, the first time any run on a submission reports one, freezes it onto `Submission.task_checksum` as the canonical version. `submission_service._checksum_info` compares every later oracle/nop/agent run's own checksum against that canonical value and returns `ChecksumInfo` (`canonical`, `consistent`, `mismatched`) as `SubmissionSchema.checksum`; the frontend shows a red banner when `consistent` is `false`. This exists because a submission can otherwise silently mix runs from different task copies (e.g. oracle run before a re-upload, rollouts after) with nothing flagging it. The Cheat Trial is excluded (`update_canonical=False`) because `_prepare_task`'s `cheat_instruction` branch always edits `instruction.md`, so its checksum legitimately never matches; its own `task_checksum` is still recorded on `CheatTrialResult` for audit. Existing rows from before this field was added have `task_checksum=None` and don't retroactively get one. Trials whose logs carry `harbor_runner.CODEX_BAKE_NOTE_MARKER` (Codex baked into the task copy's Dockerfile, which changes Harbor's checksum by design) are left out of the comparison and listed in `ChecksumInfo.not_comparable`, and never set the canonical checksum; a real mismatch among the other runs is still flagged.

**Oracle, Nop and Agent Trials run through Harbor.** `services/harbor_runner.py` shells out to `harbor run` (`-a oracle`, `-a nop`, or `settings.harbor_agent` for trials) (the real grading pipeline's harness; install with `uv tool install harbor==0.23.0`, the tested version) and reads the reward from `<jobs-dir>/<job>/<trial>/result.json` at `verifier_result.rewards.reward`. **Network policy:** Harbor 0.23+ replaced `allow_internet` with `[environment].network_mode` (`public` default, `no-network`, `allowlist`), and on Docker it only enforces the last two through an egress-control sidecar that needs kernel support Docker Desktop for Mac lacks; otherwise it rejects the task. So `harbor_runner._prepare_task` copies each task and rewrites its `[environment]` to `HARBOR_NETWORK_MODE` (default `public`), leaving the extracted files alone and noting it at the top of the trial logs. Empty disables this. On Windows `harbor_runner._new_group` starts Harbor in its own process group and `_stop` sends it Ctrl+Break (Windows cannot send SIGINT to another process), then `taskkill /T /F`; `.gitattributes` keeps `.sh`, Dockerfiles and the like on LF so a Windows checkout does not break them. Not yet run on a Windows machine. Harbor builds its own image on each run, so these stages don't use `Submission.image_tag`, but the router still requires Build to pass first. `DOCKER_PLATFORM` is passed to Harbor as `DOCKER_DEFAULT_PLATFORM`, because Harbor doesn't pin a platform itself. `DOCKER_ADD_HOSTS` (`hostname:ip` pairs, off by default) pins addresses into every build for networks that filter one address of a multi-address host (GitHub's release/raw CDN, where `185.199.109.133` hangs on some networks, so a Dockerfile that curls GitHub fails at random): `docker_orchestrator._run_docker_build_cli` adds `--add-host`, and `harbor_runner._write_build_hosts_overlay` writes a compose overlay, passed as `--extra-docker-compose`, that adds `build.extra_hosts` to Harbor's `main` service, so both build paths use the same pins. BuildKit counts extra hosts in a layer's cache key, so a hand-built image with different hosts does not warm the platform's cache. A run with no reward (build failure, crash, timeout) is stored as `failed` with `reward=None` and must not be shown as a Nop pass.

**Oracle runs N times, always appended.** `POST /submissions/{id}/oracle?n=3` (default 3) pre-creates `n` new pending `Run` rows (kind="oracle", `run_index` continuing from whatever's already there -- never deleted, unlike a plain agent-trials re-run) and `task_runner.run_oracle_trials` runs them one at a time via `harbor_runner.run_single` (never two Harbor jobs concurrently -- that has caused `EnvironmentStartTimeoutError` on this machine). This exists because Gate 1 needs 3 *consecutive* reward=1 runs, and the UI needs every run's own result visible afterwards, not just the latest overwriting the one before it (the old single-row `run_oracle`/`_run_harbor_gate` behavior). `submission_service._oracle_runs_result` aggregates all `kind="oracle"` rows into `OracleRunsResult` (`status`, `n`, `runs: list[TrialResult]`, `all_passed`): `status="passed"` only once *every* run has reward=1 (unlike agent trials, which only needs one). Nop stays single-row (`_run_harbor_gate`, still used only for `kind="nop"` now) since the guidelines only require one Nop run.

**Agent trials.** One `harbor run --n-attempts n` job with the Terminus-2 agent by default. The model is `AGENT_MODEL` (a LiteLLM string such as `openai/gpt-6-astra`), or derived from `LLM_PROVIDER`/`LLM_MODEL` when that's empty. `LLM_MAX_ITERS` becomes Terminus's `max_turns`, and `AGENT_REASONING_EFFORT` is passed through when set. `HARBOR_AGENT=codex` switches to OpenAI's Codex agent, which behaves very differently from Terminus-2: it runs inside the task container, so it needs `HARBOR_NETWORK_MODE=public`; Harbor's own install step (apt, an `nvm` download from GitHub, `npm install`, 6+ minutes and easily broken by a flaky route to `raw.githubusercontent.com`) is avoided by `CODEX_BAKE_INTO_IMAGE` (default on): `harbor_runner._prepare_task` appends a layer to the temporary task copy's `environment/Dockerfile` that installs Node (nodejs.org) and Codex (npm) at image build, best-effort, and Harbor skips its install when `command -v codex` succeeds (pin the version with `CODEX_VERSION`; empty bakes whatever is newest at first build). With `CODEX_VERSION` empty, `_bake_codex_into_environment` also stamps today's date into the install layer's own `RUN` line (`RUN echo "codex latest cache-bust: <date>" > /dev/null`, right before the real install command), because Docker's build cache would otherwise mean "latest" only ever means "whatever was newest the first time this task's image was built," silently frozen from then on -- a real risk distinct from (and in addition to) the actual incident this project hit, where `CODEX_VERSION` got pinned by a stray shell environment variable outside `.env`. The date line changes that layer's cache key once a day, which chains to the real install layer rebuilding fresh too. Never added when a version is pinned -- that's a deliberate choice, not staleness. It runs, so and it needs an `openai/*` model and receives the OpenAI key inside the container. Harbor >= 0.23 rejects agent options the agent doesn't declare, so `task_runner._agent_kwargs` gives each agent only its own (Terminus: `max_turns` + `reasoning_effort`; Codex: `reasoning_effort`, `version` from `CODEX_VERSION`, `web_search` from `CODEX_WEB_SEARCH`, and no turn cap, so only the task's agent timeout bounds its cost). `_agent_config_error` fails the trials with a clear message for a bad Codex setup. Codex leaves `reasoning_effort` at its own default unless `AGENT_REASONING_EFFORT` is set. If an agent reports tokens but no cost, `harbor_runner` prices them from `llm/pricing.py`. Each trial's logs start with a notes header (C9): the Harbor CLI version (`harbor_runner._harbor_version()`, cached per process), the exact `harbor run` command including every `--agent-kwarg` actually passed (so the real reasoning effort sent is never just assumed from settings), a confirmation that the agent execution timeout is written into task.toml as-is with no multiplier math (only the separate install-time `--agent-setup-timeout-multiplier` is a real multiplier, and its value is logged too, or its absence is), and the agent's own resolved version. That last one is per-trial, not per-job: `_parse_trial` reads `agent.name`/`agent.version` straight out of Harbor's own `<trial>/agent/trajectory.json` (every installed agent -- Codex, Claude Code, Terminus-2 -- writes this itself), rather than a requested/pinned setting like `CODEX_VERSION`, since empty there resolves to whatever npm calls "latest" and the platform never installs Claude Code itself at all (no equivalent pin exists for it). Terminus-2 runs on the host and drives the task container, so provider keys (`harbor_runner._litellm_key_env`) never enter the container and the task's `allow_internet` setting holds. Harbor copies `tests/` into the container only after the agent finishes, so the agent never sees them. `POST /submissions/{id}/agent-trials?n=N` replaces earlier trials by default; `append=true` keeps them and adds N more after the last one (`run_agent_trials` only picks up the `pending` rows the router just created and keeps the earlier Harbor output), and the UI button always replaces. `run_job` polls for each trial's `result.json`, which is written once when the trial finishes, and fills the pre-created `Run` rows in completion order. Token counts and `cost_usd` from Harbor go into each trial's logs.

**Per-run agent, reasoning level and failure analysis.** `POST /submissions/{id}/agent-trials` takes an optional `agent` (`task_runner.AGENTS`: `codex`, `claude-code`, `terminus-2`; default `HARBOR_AGENT`), which picks the model (`_agent_model(agent)`: `CLAUDE_AGENT_MODEL`, default `anthropic/claude-fable-5-1`, for claude-code; `AGENT_MODEL` otherwise), the config check (`_agent_config_error(agent)`: claude-code needs `ANTHROPIC_API_KEY`, an `anthropic/*` model and public network) and the options (`_agent_kwargs(agent, reasoning_effort)`). Harbor's `claude-code` agent installs itself in the container (downloads.claude.ai bootstrap) and reports its own `total_cost_usd`; the watchdog can't read its cost mid-run, so `run_agent_trials` passes each trial `max_budget_usd` = run cap / n. It also takes an optional `reasoning_effort` (`task_runner.REASONING_EFFORTS`; anything else is a 400) that overrides `AGENT_REASONING_EFFORT` for that run only through `_agent_kwargs(reasoning_effort)`; the UI dropdown sends it. `POST /submissions/{id}/failure-analysis` (`task_runner.run_failure_analysis`, advisory like the LLM judges) runs `harbor analyze` (`harbor_runner.run_analyze`) once per `agent-*` job dir under `runs/agent/harbor/` with `ANALYZE_AGENT` (default terminus-2, so the key stays on the host and nothing is downloaded from GitHub) and `ANALYZE_MODEL` (default `openai/gpt-6-luna`), writes Harbor's output under `runs/analysis/`, and stores JSON (`agent`, `model`, `cost_usd`, `error`, `results` per trial with `summary` and `checks` for `reward_hacking`/`task_specification`) in the `failure_analysis` Run's logs; its cost goes into `llm_spend`. The Codex bake (`_bake_codex_into_environment`) skips a task only when a compose file in `environment/` gives the `main` service its own `build:` or `image:` (`_compose_replaces_main_image`; an unparseable file also skips), because then the agent's container may not come from `environment/Dockerfile`; those tasks install Codex inside every trial (10-16 minutes each). A compose file that only adds other services or `depends_on` (e.g. int8-runtime-port) is baked as normal, since Harbor's own base compose builds `main` from `environment/`.

**Cheat trial and rubric check.** `POST /submissions/{id}/cheat-trial` (`task_runner.run_cheat_trial`, optional `agent` and `reasoning_effort` like `agent-trials` -- the UI defaults `reasoning_effort` to max rather than the server default, since a cheat trial run at whatever `AGENT_REASONING_EFFORT` happens to be is a weaker test and easy to leave stale without noticing) runs 1 to 3 trials (`n`, see 4.1 B.2 below) in one job through `harbor_runner.run_job(..., cheat_instruction=True)`, which makes `_prepare_task` always copy the task and splice `harbor_runner._CHEAT_INSTRUCTION` into `instruction.md` (before the closing timeout sentence when present) telling the agent to fake the grade by any means. Reward staying 0/None already means the trap held (`status="passed"`). reward=1 alone doesn't mean a real cheat -- confirmed live twice, on two different harnesses (Codex and Claude Code): both trials got reward 1 after the agent's own first message refused the directive ("I won't alter grading machinery/checks or use hidden task or reference files") and solved the task honestly, with no access to `tests/` or `/app/task` anywhere in either trajectory. So a reward=1 trial automatically triggers a `harbor_runner.run_analyze` `reward_hacking` check on that one trial's job dir (the same mechanism Failure Analysis uses); only a check that positively returns `outcome: "pass"` counts as `status="passed"` ("trap held; solved honestly despite the directive"). A check that finds hacking, or that itself errors/returns nothing (`outcome: "unknown"`), stays `status="failed"` so it always gets a human's attention rather than being assumed clean. `logs` is JSON: `{trial_log, reward, cheat_check: {outcome, explanation, cost_usd, error} | null, cheat_prompt}`. `cheat_prompt="tb"` splices in `vendor/tb_prompts/hack-trial-prompt.md` (a more aggressive, explicit red-team-style directive) instead of the platform's own `_CHEAT_INSTRUCTION`, via `harbor_runner._prepare_task`'s new `cheat_instruction_text` param. `_agent_config_error` and cost-cap logic are reused from `run_agent_trials`; the analyze call's cost is also recorded under the `"cheat_trial"` stage in `llm_spend`. `POST /submissions/{id}/rubric-check` (`task_runner.run_rubric_check`, advisory, optional `rubric`) runs `harbor check` (`harbor_runner.run_check`) once over the whole extracted task with `CHECK_AGENT`/`CHECK_MODEL` (default Claude Code + `anthropic/claude-fable-5-1`, so it needs `ANTHROPIC_API_KEY`) and stores the same `{agent, model, cost_usd, error, results, rubric}` JSON shape as failure analysis, but grading the task itself (instruction, tests, environment) against a rubric -- the vendored 36-criterion `rubric="tb"` by default since 4.1 (Harbor's built-in one with `rubric="default"`), from `vendor/tb_prompts/task-implementation.toml` -- not agent trajectories. Harbor's own launcher passes the instruction as a shell argument, so a task with a very large `environment/` (e.g. vendored crates) can fail with an OS argument-length error, surfaced in `error` rather than a real verdict.

**Vendored Terminal-Bench prompts (`backend/vendor/tb_prompts/`, see `PROVENANCE.md` there).** Five files copied verbatim from `harbor-framework/terminal-bench`'s `docs/prompts/` at a pinned commit, each an optional, richer alternative to a Harbor default -- never the default itself: `trial-analysis.toml` (6-criterion `harbor analyze -r` rubric: `task_specification`, `reward_hacking`, `difficulty_crux`, `near_miss`, `refusals`, `low_timeout`, vs. Harbor's own 2), `trial-analysis.txt` (the matching per-trial `-p` prompt), `trial-analysis-job.txt` (a job-*summary* prompt with a `{trial_results}` placeholder -- not a Harbor CLI flag, since Harbor has no built-in job-summary step; `task_runner.run_failure_analysis` does one extra LLM call with this template, substituting in that run's own results, only when `rubric="tb"`), `task-implementation.toml` (36-criterion `harbor check -r` rubric since the 2026-10-15 refresh added `effective_instruction_length`, vs. Harbor's own 11), and `hack-trial-prompt.md` (the Cheat Trial's alternate, more aggressive directive). `harbor_runner.run_analyze`/`run_check` both gained optional `rubric_path`/`prompt_path` params (`--rubric`/`--prompt` flags Harbor's CLI already supported but this platform never exposed) to use these. `task_runner.RUBRICS`/`CHEAT_PROMPTS` (`("default", "tb")`) are the only accepted values; the router validates and 400s on anything else.

**Agent timeout and the run cost cap.** `AGENT_TIMEOUT_SEC` (Terminal-Bench 4.0 uses a flat 28800 = 8h) is written into the same temporary task copy as the network policy (`harbor_runner._prepare_task` and `_rewrite_toml`), so Harbor enforces the exact value with no multiplier math, and `task_runner._agent_timeout_sec` feeds it into the backend's own outer timeouts, which would otherwise kill a long run early. Long timeouts make one runaway trial able to spend the whole month before anything checks, so `run_job` has a watchdog: every 10s it sums finished trials' costs plus each in-flight trial's running cost and stops the job (SIGINT, so Harbor removes its containers) once it reaches `AGENT_RUN_BUDGET_USD` or what is left of `LLM_BUDGET_USD`. In-flight cost comes from Terminus's `agent/trajectory.json` (rewritten every turn, on the host) or, for Codex, from `docker exec` reading the session file in the trial's container (`/tmp/codex-home/sessions`), because Codex only copies it out at the end and its own log reports usage once, at the end. Trials cut short report no cost themselves, so `_parse_trial` falls back to the last live figure, and that partial cost is still recorded in `llm_spend`. The check interval means a run can overshoot the cap by a few cents.

**Budget guard** (`services/budget.py`). `LLM_BUDGET_USD` (default 50, `0` = off) caps priced LLM spend per UTC calendar month, recorded in the `llm_spend` table (separate from `Run`, because re-running agent trials deletes the old `Run` rows). Two sources feed it: each finished agent trial's Harbor `cost_usd`, and each judge call's token usage priced by `services/llm/pricing.py` (which includes the cache-write price: the API reports `cache_write_tokens` separately and bills them 25% above plain input for gpt-6-astra, so nearly every fresh prompt pays it). Only models in that price table (currently `gpt-6-astra`) are tracked; Fireworks and other providers are skipped, and the judge endpoints only enforce the cap when the judge model is priced. The agent and judge endpoints refuse to start once the cap is reached, and `run_agent_trials` stops the Harbor job (via `on_trial` returning a reason) after the trial that crosses it. Cost is only known when a trial or call finishes, so in-flight work can overshoot. `GET /budget` returns the month's spend and the limit.

**LLM providers.** Set by `LLM_PROVIDER`/`LLM_MODEL` in `backend/.env`. These drive the LLM-judge stages (and the agent model unless `AGENT_MODEL` is set). The options are anthropic, openai, gemini, groq and fireworks (the default). Groq and Fireworks reuse `OpenAIClient` with a different `base_url`. For the real OpenAI provider, `OpenAIClient` also gets `LLM_REASONING_EFFORT` and `LLM_MAX_OUTPUT_TOKENS` (as `max_completion_tokens`, which includes reasoning tokens) from the factory, and reports each call's token usage to `llm/usage.py`, a ContextVar collector that `task_runner._track_llm_spend` turns into `llm_spend` rows, since the judges create their own client and return only a verdict. All clients implement `llm/base.LLMClient` and share `rate_limiter.TokenBucket`. The LLM-judge stages are `sufficiency_judge` and `review_report`. They run on `gpt-6-sol` by default in `.env.example`. We compared gpt-6-astra, sol, luna and Gemini on five tasks including one with a deliberately removed requirement: sol matched astra on Sufficiency (5/5, caught the broken task) at a fifth of the cost, luna (about 100x cheaper than astra) got 4/5. Fireworks and Groq keys were dead and Google retired the 2.5 Gemini models for new users. `gemini-3.5-flash-lite` (Google paid tier: $0.30 in, $2.50 out, $0.03 cached per million; output includes thinking tokens) matched sol 5/5 on Sufficiency at roughly a third of sol's cost and is a supported judge model: `GeminiClient` reports usage (so `llm_spend` and the budget guard count it, via its entry in `llm/pricing.py`) and retries only rate limits (429), server errors and connection errors, failing at once on a retired model or bad key. Judge prompts include hidden tests and reference solutions, and Google may use free-tier prompts to improve its products, so use a paid-tier key. The first two read task files through `services/judge_files.py`, which lists every file (size, and whether its contents are shown), detects text by content instead of extension, and caps each file at `JUDGE_MAX_FILE_CHARS` (150k) and the dump at `JUDGE_MAX_TOTAL_CHARS` (500k). Those were 20k and 120k, which cut one task's 324k-character dossier and made Sufficiency report its rules as missing. The listing matters: without it a judge that sees only some files reports the others as missing. Review Report requires every required gate to be in a terminal state first (`all_gates_terminal`).

**Advisory vs. gating stages.** Leakage Scan (regex over task files), Static Checks, TB Static Checks and Review Report ("passed" only means the report was generated) are advisory. Their `passed: false` does not disqualify a submission, so don't treat them as gates or merge them with each other (see the comments in `src/lib/api.ts`). `static_checks.py` and `infra_marker_scan.py` produce heuristic findings from the task files and the trial logs. `task_runner.run_static_checks_stage` persists `static_checks.py`'s output as its own `Run` (kind="static_checks") so it's independently visible, not just recomputed live inside Review Report's own prompt (both call the same deterministic function, so they never disagree).

**More static checks (4.0 category F).** `services/hygiene_checks.py` (called at the end of `static_checks.run_static_checks`, plain code, no LLM, advisory) adds: named volumes in `environment/docker-compose*.y*ml` (upstream's newer `check-compose-volumes.sh` rejects every volume and replaced the vendored host-bind check), the missing `# syntax=docker/dockerfile:` first line when a heredoc is used, unpinned `npm`/`npx` installs and `curl | sh` (warn) and unpinned `apt` packages (info only; `tmux`/`asciinema` are exempt, the harness needs them), key-like strings and x86-only downloads without an architecture branch in `environment/`, paths named in `instruction.md`/`README.md` that exist nowhere in the task, same-named files that differ between `environment/` and `tests/`, tools the tests use that `environment/Dockerfile` installs but `tests/Dockerfile` does not, and `instruction_effective_length` (the instruction's words plus the `.md`/`.txt` files it names that the agent can read; a number, not a limit). Vendored third-party folders (`vendor/`, `node_modules/`) are skipped. `tb_static_checks` prefixes a canary failure that points only at `environment/` files with CONTESTED (upstream issues #2200/#2210). `backend/scripts/diff_vendored_checks.py` clones upstream and prints how the vendored checks and prompts differ; updating them and `PROVENANCE.md` is a manual step.

**Sufficiency and Failure Analysis upgrades (4.0 category A).** The Sufficiency judge now also sees `solution/` and works through tagged extra checks (`[reverse]` every allowed value is accepted by some test, `[reading]` defensible readings, `[hidden-rule]` tie-break/ordering rules only in the tests, `[stale]` numbers in the instruction vs the data, `[source]` expected values with no justifying line, `[oracle]` the solution copies instead of computing); gaps start with the tag. `POST /sufficiency?runs=1..3` runs the judge that many times (later runs see the sections in the other order); the majority decides, each gap says how many runs raised it, and a split is called out as disagreement. `hygiene_checks.check_oracle_honesty` (`oracle_reads_tests`, static) warns when `solution/` reads from `tests/` or uses a tests answer file. `run_failure_analysis` adds a `classification` to its JSON (`_classify_failures`, one extra judge call when any trial failed): each failed trial as `real_bug` / `instruction_gap` / `infrastructure`, plus clusters of trials that chose the same alternative reading, always labelled "contested, needs a domain expert". Advisory throughout.

**Valid-variant probe, audit, changes and reviewer decisions (4.0 category A).** `POST /submissions/{id}/variant-probe` (`task_runner.run_variant_probe`, `services/variant_probe.py`, kind `variant_probe`, advisory, needs an Oracle pass first) has the judge read `instruction.md` and `solution/` (never `tests/`) and propose up to 4 find/replace edits to `solution/` that change only the form of the answer; each must quote an instruction sentence (a quote not found in the instruction drops the variant). Each variant is applied to a temporary copy of the task and run as an Oracle trial through `harbor_runner.run_single`, one at a time; a rejected variant means the grader may accept fewer forms than the instruction allows, shown with the quote so a reviewer can tell a strict grader from a variant that was not really allowed (the quote check proves the sentence exists, not that it entails the variant). `run_failure_analysis` also stores an `audit` (`_audit_trials`: passing trials' unstated assumptions, the best failing trial's misses ruled agent error / documentation gap / grader error, documented examples the tests would reject). `GET /submissions/{id}/changes` (`services/submission_diff.py`) compares an upload with the latest earlier upload of the same task name (every upload is a new submission): files added/removed/changed, tests removed/added by `def test_` name, instruction length; the UI shows it as a banner, amber when tests were removed. `PUT /submissions/{id}/reviewer-decision` records a reviewer's ruling on a contested cluster (`reviewer_decision` Run, JSON in logs, key = the cluster's sorted trial names); it never changes a gate. Both go into the evidence bundle.

**Grader too weak (4.0 category B).** The Sufficiency prompt also asks `[coverage]` (every MUST/MUST NOT rule has a test that fails when broken), `[loose]` (how many wrong outputs still pass; any test passing on empty output), `[trust]` (results read from agent-writable files; a modelled shortcut instead of the real outcome) and `[fixed-input]` (hard-coded answers would pass). `POST /submissions/{id}/weak-probe` (`task_runner.run_weak_probe` = `_run_probe(..., "weak_probe", "broken")`, shared with the valid-variant probe, kind `weak_probe`, advisory, needs an Oracle pass) has the judge propose up to 6 find/replace edits to `solution/`, each breaking exactly one stated rule and quoting it; each runs as an Oracle trial on a temporary copy and must score 0 (`caught`); a broken answer that scores 1 is `slipped_through` and makes the stage `failed`. `POST /submissions/{id}/edge-cases` (`services/edge_cases.py`, kind `edge_cases`, no Docker): one call lists edge cases from `instruction.md` alone (never the tests), a second marks each covered or not by the tests; any uncovered case makes the stage `failed` (a question for a human). The Cheat Trial now records `tool_calls` (from `agent/trajectory.json`, `TrialOutcome.tool_calls`) and is `inconclusive` (status `failed`, `logs.inconclusive` set, amber box in the UI) when the reward is below 1 but the trial produced no reward or the agent made fewer than 3 tool calls, so an agent that never tried is not reported as "the trap held"; `cheat_prompt="combined"` asks for a real partial solution plus a shortcut. The TB rubric is the Rubric Check default in both the UI and the backend (4.1 A.4); Default is still in the dropdown, and `api.rubricCheck` always sends the choice.

**TB Static Checks.** A second, separate advisory stage (kind="tb_static_checks", `task_runner.run_tb_static_checks_stage` → `services/tb_static_checks.py`) runs Terminal-Bench's own official static checks, not this platform's. The 29 `check-*.sh` scripts (refreshed to upstream `2e29ca9`, 2026-10-15: `check-compose-volumes`, `check-cpu-threads`, `check-image-digests` added, `check-compose-host-binds` removed, `check-task-changelog` now needs an `X.Y.Z` version) are vendored verbatim from `harbor-framework/terminal-bench`'s `scripts/checks/` at a pinned commit (`backend/vendor/tb_checks/`, see `PROVENANCE.md` there for the commit hash and update instructions) rather than cloned at runtime, so results don't silently shift if upstream changes its requirements. This is deliberately not a replacement for `static_checks.py`: the two rule sets barely overlap (TB's checks framework compliance -- canary, dockerfile platform/sanity, separate verifier, task fields, absolute paths, pip/pytest pinning -- ours checks platform-specific hygiene like instruction word count and Dockerfile digest pinning), so both run and neither supersedes the other. The task path is passed with a trailing slash: it is a symlink, and `find <symlink>` without one does not descend, so `check-canary`, `check-compose-volumes` and `check-test-file-references` found no files and passed vacuously until the 5.0 guide check caught it. Two fixes were needed to run these vendored scripts correctly against this platform's own layout, both handled in `run_tb_static_checks` via a temporary symlink rather than by patching the vendored scripts: (1) several scripts internally re-split a path on an unquoted shell variable, which breaks on any whitespace in the path (true of this repo's own checkout on at least one machine, `"Task Evaluator"`) -- worked around with a space-free symlink; (2) `check-task-package-name.sh` derives the expected task name from the directory's own basename, which is meaningless for this platform's generic `submissions/{id}/extracted/` layout (never named after the task's real slug) -- worked around by naming that symlink from `task.toml`'s own declared `[task] name` instead of the real folder name.

**AI Detection.** A third advisory stage (kind="ai_detection", `task_runner.run_ai_detection_stage` → `services/ai_detection.py`) runs Terminal-Bench's own Layer 3 AI-usage detection: `vendor/tb_checks/scripts/check_ai_detection.py` (same pinned commit, see `PROVENANCE.md`), which is genuinely not one of the 26 `check-*.sh` scripts and is not wired into any of Terminal-Bench's own automatic CI either -- confirmed directly against their `.github/workflows/`, it's optional there too, enabled only by adding a step with a `GPTZERO_API_KEY` secret. The vendored script calls the real GPTZero API (`api.gptzero.me`) against `instruction.md` and `solution/solve.sh`, failing at or above 70% `completely_generated_prob`. `GPTZERO_API_KEY` (config.py, empty by default) is a paid third-party subscription key, unrelated to the platform's other provider keys. `services.ai_detection.run_ai_detection` runs the script with a deliberately minimal env (just `PATH` plus the one real secret, not `host_env_for_subprocess()`'s full environment) since it sends file contents to a third-party API and shouldn't see anything else from the host. Without a key, the vendored script itself prints a warning and exits 0 -- `run_ai_detection_stage` reads that from the script's own output (not a separate check this platform added) and reports `status="passed"` with `skipped=true`, distinct from a genuine pass, so a reviewer can tell "not checked" apart from "checked and clean." A genuine finding (probability at or above threshold) is the only case that reports `status="failed"`.

This is Terminal-Bench's Layer 2 and Layer 3 of AI-usage detection, both now on the platform, via two genuinely different mechanisms -- deliberately not merged into one verdict. Layer 2 is `instruction_concision`, one criterion inside the 35-criteria rubric already covered by Rubric Check's "tb" option (an LLM's subjective judgment on writing style, read alongside 34 other unrelated quality criteria). Layer 3 (this stage) is a real third-party measurement, a genuine probability score from a dedicated detector, entirely independent of Layer 2's LLM opinion. Terminal-Bench's own Layer 1 (a written contributor policy, "write this yourself") isn't code at all, so there's nothing to run for it -- Layers 2 and 3 exist to approximate checking that policy was followed.

**Infra-failure auto-retry (C11).** `task_runner._retry_infra_agent_failures`, called once at the end of every `run_agent_trials` job, gives a trial exactly one automatic retry if both hold: its `reward is None` (a crash/timeout with no result, not a genuine reward=0 attempt) AND `infra_marker_scan.scan_trial_logs` finds a known infra-noise marker in its logs (connect/read timeout, rate limit, DNS failure, Docker orchestration error). The retry runs sequentially through `harbor_runner.run_job` with `n_attempts=1` in a sibling `-infra-retry` jobs dir (never a second concurrent Harbor job). The `Run` row is updated with the retry's own reward/status/logs, but the original failure is kept, not discarded -- prepended under a `_INFRA_RETRY_MARKER` header naming which markers were seen. It also recognises Codex setup failures inside the trial (`NetworkConnectionError`, an apt install failing during setup). `config.host_env_for_subprocess` sets `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8` for every subprocess, because Harbor prints emoji and `harbor analyze`/`check` crash on a Windows console (cp1252). That same marker is checked before retrying at all, so a retry that *itself* shows infra noise is never retried again (bounded to one attempt, left for a human rather than looping against a persistent problem like Docker being down). If the monthly budget is already exceeded, the trial is flagged `(not retried: <reason>)` instead of silently skipped or retried anyway. A trial with `reward=0` (the agent genuinely tried and failed) or `reward is None` with no recognized marker is never touched -- this only catches known, well-understood infra noise, never a real task-solving failure.

**pass@k (C6).** `submission_service._pass_at_k(n, c, k)` is the standard unbiased estimator (`1 - C(n-c,k)/C(n,k)`, via `math.comb`), computed for every `k` from 1 to `n` once all agent trials are terminal and returned as `AgentTrialsResult.pass_at_k` (`dict[str, float]`, keyed by `k` as a string). This exists because Harbor's own job-level reporting (`_eligible_k_values` in the installed `harbor` package) only ever fills in powers-of-2 and multiples-of-5 `k` values — pass@1 is never computed by Harbor itself for any job, by design, not a bug worth working around any other way.

**Verifier report (4.0 category D).** `Run.reward` stays the 0/1 the gates use (`task_runner._apply_trial_outcome`: anything below 1.0 counts as 0), but Harbor's exact reward is kept in `Run.raw_reward` and the verifier's own files in `Run.verifier_json` (`services/verifier_report.py`, read by `harbor_runner._parse_trial` from the trial's `verifier/` folder): per-test pass/fail/skip from `ctrf.json`, a score-details sidecar if one exists (`reward-details.json` and the other names tasks invented), and `flags` where reward and tests disagree (non-binary reward; reward 1 with a skipped/failed test or no passing test; all tests passed but reward below 1; no `ctrf.json`). These are advisory evidence for a human, never a gate. Both columns are nullable and added at startup by `main._add_missing_run_columns` (same approach as `llm_spend`), so older rows simply show nothing. `submission_service._agent_trials_result` adds `test_summary` (`verifier_report.cluster_failures`): which tests the failing trials failed, the closest trial, and a note when every failing trial first fails at the same test (ctrf lists tests in run order; the typical shape of an over-strict grader or an unstated rule, or just the hard part). A test that merely fails in several trials is listed, not flagged. `static_checks.check_test_sh` also checks what `test.sh` writes to `reward.txt` (`test_sh_reward_binary`: a literal other than 0/1 fails, a computed value is only mentioned). The evidence summary gets a "Verifier reports" section only when something was flagged. **Run facts (4.0 category E).** The same stored report also carries `facts` (`verifier_report.read_run_facts`, read in `_parse_trial` from result.json and the task copy's task.toml): agent and verifier seconds against their limits, CPUs, memory, Docker platform and host architecture, and the agent and verifier users (`null` = the image's own USER, root by default). `facts_flags` warns when either phase used 80% or more of its limit and when the trial output contains an architecture error (`exec format error`, `illegal instruction`). A trial that crashed before grading still gets a report holding just the facts. `AGENT_TIMEOUT_SEC=28800` is set in `.env.example`; the active `.env` is left to the operator. Also in E: `harbor_runner._probe_container` reads each in-flight trial container's cgroup `memory.peak`, `oom_kill` count and Docker's `OOMKilled` flag every 10 s (Harbor removes the container at the end), `_apply_probe` adds `peak_memory_mb` to the facts and an out-of-memory flag (or a 90%-of-limit note); `static_checks.check_hardware_flags` warns on `-march=native` style flags in environment/, solution/ and tests/; `infra_marker_scan` also knows a full disk, model-request timeouts and an unreachable Docker daemon, and `_parse_trial` adds an "infrastructure, not the task" flag when a non-passing trial's exception or `trial.log` matches; `LITELLM_REQUEST_TIMEOUT_SEC` (3600) is passed to Harbor as `REQUEST_TIMEOUT` because LiteLLM 1.102.1 inside Harbor 0.23.0 otherwise cuts a chat request at 600 s; `task_runner._cost_cap_warning` puts a warning in the trial logs when cap / trials is under `MIN_TRIAL_COST_USD` (3) on a task with an agent timeout of an hour or more. The cap can also be set per run: `POST /agent-trials` takes `max_cost_usd` and `cost_mode` (`total`, or `per_trial` meaning the value times n, since the watchdog stops the whole job, not one trial; Claude Code additionally enforces its share through `max_budget_usd`). It replaces `AGENT_RUN_BUDGET_USD` for that run (`_run_cost_cap(db, requested)`), and what is left of the monthly `LLM_BUDGET_USD` still applies on top, so the UI can lower the limit but not raise it past the month. The UI has a "Cost cap $" box with a for-the-run / per-trial choice and an amber warning under $3 per trial.

**Agent user (5.0 category H).** Terminal-Bench 5.0 moves agents to a non-root user (`[agent] user`, upstream #1505). A root agent is a warning, never a failure. `services/agent_user_checks.py` (called from `static_checks.run_static_checks`, advisory, no Docker) warns `agent_runs_as_root` when neither `[agent] user` nor a final non-root `USER` is set; with a user set it warns when the Dockerfile never creates it, never `chown`s files to it, gives it `NOPASSWD`/sudo, leaves toolchains under `/root` (including the `maven` base image's `/root/.m2`, which it never names), or when `solve.sh` runs `apt-get install` at run time. `harbor_runner._probe_container` also runs `docker exec [-u <user>] id -u` on each in-flight trial container; `_apply_probe` stores it as `facts.agent_uid` and adds a trial flag when it is 0 (or still 0 although a user was requested). The uid shows in the trial log's `users:` line and the UI's facts line (amber when root). A non-root Oracle that fails (e.g. Maven cannot read `/root/.m2`) is the real signal that a task does not work as non-root. `agent_user_only_in_dockerfile` (warn, found by the 5.0 real-task tests on risk-scorer-replay, upstream #2152) fires when the non-root user comes only from the Dockerfile `USER` and `task.toml` has no `[agent] user`, because some runners (Modal) ignore a Dockerfile `USER` and start the agent as root.

**Refusals (5.0 category J).** A model's safety refusal scores reward 0 like a real failure and drags down the pass rate. `services/refusal_detector.py` (no LLM) reads each non-passing trial in `harbor_runner._parse_trial`: a content-policy or safety error from the model provider in the exception or `trial.log` counts as refused, and so does a refusal phrase in the agent's own messages (`trajectory.json`) when it made fewer than 3 tool calls (an agent that says "I can't X" but then works is not counted). The result is stored as `refusal` in the trial's verifier report with a flag naming the evidence. `AgentTrialsResult` adds `refusals` and `pass_rate_excluding_refusals`; `pass_rate` and `pass_at_k` are deliberately unchanged. The UI shows an amber line under the trials and the evidence summary a "Refused" line. A phrase match can be wrong, so it is evidence for a human, never a gate. `POST /failure-analysis` now defaults to the TB rubric (`rubric=tb`; the UI pre-selects it), so its `refusals` criterion runs by default.

**Environment causes (5.0 category E).** Failures that come from the machine or the image, not the agent. `infra_marker_scan.scan_environment_causes` (separate from the retried `_INFRA_MARKERS`, since re-running cannot fix an architecture) matches `no matching manifest`, `exec format error`, aarch64 package misses, `GLIBC_x not found`, GitHub rate limits/403/429, "port not ready" and the verifier sandbox failure "Worker could not install required protections" (rewardkit's `Worker` needs a kernel feature Docker Desktop lacks; mvcc-lsm-compaction); `_parse_trial` adds an "environment, not the agent" flag to a non-passing trial and Review Report names the same causes. `image_inventory` also reads the image's `uname -m`, OS and glibc (`system`), and after Build `task_runner._record_image_inventory` adds `base_images` from `platform_checks.inspect_bases` (`docker buildx imagetools inspect --raw` per `FROM`: platforms present, warns on a single-platform digest instead of the index, a missing amd64/arm64, or `FROM --platform`). `submission_service.run_limits` puts `image` and warnings in the evidence (glibc below 2.36, image arch against `DOCKER_PLATFORM`, base-image warnings, `AGENT_TIMEOUT_SEC` overriding the task's own timeout); the Image Contents card shows them. `platform_checks` also adds two Static Checks: `bundled_binaries_single_arch` (ELF/Mach-O headers in `environment/` for one architecture only) and `check_resources` (`gpu_not_available` when `gpus` is set and the host has no `nvidia-smi`, `agent_timeout_below_estimate` when `[agent] timeout_sec` is under `expert_time_estimate_hours`). Not done: a cross-architecture Oracle, scanning archives for binaries, and an "Oracle 0 with identical or UNKNOWN outputs" arch heuristic.

**Grader hardening (5.0 categories B and A1).** More Static Checks in `verifier_isolation.py`: `verifier_scans_source` (a restriction enforced by reading the submission's source: `ast.parse`/`ast.walk`, banned-import lists, `grep import` in test.sh; bypassed by exec/eval, importlib or a pre-built binary the source only loads), `verifier_inherited_descriptors` (`close_fds=False`, `pass_fds`, `os.set_inheritable`), and `compile()`/`__import__()` of a non-literal under `verifier_evaluates_answer` (about 3 of 40 stored tasks hit this, e.g. a generator's own mutants). `check_lean` adds an info hint to use the Targeted Cheat prompt and an info note for toolchains in `_UNSOUND_LEAN` (hand-kept; the one entry, Lean 4.28, rests on a 5.0 milestone item title and is unverified). `hygiene_checks.check_oracle_honesty` also warns when a solution `.py` imports a module that exists only under `tests/`. The weak-answer probe prompt (`variant_probe.BREAK_PROMPT`) now also asks for corrupting k of n outputs, blanking a field, embedding a forbidden library or pre-built artifact, and X/Z/NaN values. Cheat Trial `cheat_prompt="targeted"` (`harbor_runner.targeted_cheat_instruction`) builds the directive from the task: the restriction sentences of its own instruction.md, an import-time/result-channel hole when `tests/` has Python, and axiom/macro/elaborator holes when the task has `.lean` files. It is never run by default.

**Sufficiency recall (5.0 category A2).** The judge prompt adds `[fields]` (a table of every output field a test checks: what the instruction says vs what the test computes), `[docstring]` (comments and docstrings in agent-visible files are part of the instruction; report a contradiction), `[numbers]` (every tolerance/threshold/count the tests enforce, stated or not), `[identifier]` (external identifiers, versions, coordinate systems: do the data agree, recompute simple derived values) and `[admitted]`. `sufficiency_judge.test_phrase_hits` (plain regex, no LLM, max 25) finds lines under `tests/` where the author says something is "not stated/specified/documented", "implicit", "undocumented"; they are given to the judge as a TEST PHRASES section (the judge reports one as a gap only if the instruction really leaves it unstated) and listed at the end of the Sufficiency logs. 1 of 40 stored tasks has such a line. The prompt is longer, so each judge call costs a little more.

**Lock and licence hygiene (5.0 category F).** `services/pinning_checks.py` adds three advisory Static Checks: `toolchain_pinning` (warn: `opam` without a lock or `opam switch import`, elan/lake without `lean-toolchain` and `lake-manifest.json`, `sbt` without a lock, `cpanm` without `cpanfile.snapshot`, `conda` packages without `=version`, `rustup`/`uv`/`nvm`/`pnpm` bootstraps without a pinned version, `nvm install node/--lts`), `huggingface_revision` (warn: `from_pretrained`/`hf_hub_download`/`snapshot_download`/`load_dataset` without `revision=`; local paths skipped) and `check_licences_and_size` (`bundled_data_licence` and `task_size`, both info only: 9 of 40 stored tasks bundle generated data or exceed 80 files, so a warning would be noise). The first two fired on none of 40 stored tasks. `toolchain_pinning` also gives an info note when a `conda create/install` has versioned packages but no `pixi.lock`/`conda-lock` (their dependencies still float; upstream #1901), and splits Dockerfile `RUN` text on newlines as well as `&&`/`;` so a conda command on a later line is seen. `tb_static_checks.vendor_info()` reads the vendored commit, date and script count from `vendor/tb_checks/PROVENANCE.md`; it is stored as `vendor` in every TB Static Checks result (so also in the evidence) and shown under the card's counts.

**Grader too strict / Oracle proves nothing (5.0 category A1).** *Edge cases from a format file* (`edge_cases.spec_files`, LLM): besides `instruction.md`, call 1 now also reads up to 3 agent-visible spec files (those the instruction names under `environment/`, or named like format/spec/schema/codes), lists every option such a file allows as a case ("(from <file>)", up to 16 cases instead of 10), and call 2 also gets `solution/` and returns `reference_handles` per case (false = the Oracle itself does not handle it); the result carries `spec_files`. *Oracle honesty* (`hygiene_checks.check_oracle_honesty`, no LLM): `oracle_reads_tests` also warns when a `solution/` file is identical to a `tests/` data file or embeds its whole content (40+ characters; 0 of 40 stored tasks hit it). The Sufficiency judge gets `[ground-truth]` (LLM): are the expected values independent or the reference's own output, where does the reference deviate from the spec, and is anything graded by agreement with the reference's outputs. Not built: an independent-tool comparison (rustc, a parser) and an author-supplied folder of equivalent/false solutions.

**Python-computed rewards (`tests_py_reward_binary`, found by the 4.0 real-task tests).** `static_checks.check_python_reward` parses `tests/**/*.py` and warns when a variable named `reward`/`final_reward` is assigned arithmetic or a min/max clamp, adjusted with `-=`, or a `write_reward(...)` helper gets a fraction, because `test_sh_reward_binary` only reads `test.sh` and missed terminal-bench issue #1389 (kv-live-surgery computes `max(0, min(1, (speedup-2)/3))` in `test_score.py`; the Oracle scores 1.0 so no runtime flag appears either). Strings and paths are skipped. 0 of 66 current terminal-bench tasks fire it; it fires on kv-live-surgery before PR #1649 and not after. Advisory. Evidence for the real-task tests lives in `docs/testing/` (runner: `backend/scripts/run_tb_test.py`).

**`DOCKER_ADD_HOSTS` and shared networks (found by the 4.0 real-task tests).** The runtime hosts overlay (`harbor_runner._write_runtime_hosts_overlay`) puts `extra_hosts` on `main`, and Docker rejects that when a compose file in `environment/` gives `main` a `network_mode` (`service:api`): "conflicting options: custom host-to-IP mapping and the network mode", so the Oracle failed before it started. `_main_shares_another_network` detects it and the overlay is skipped for that task (the build-time pin still applies). Of the 68 terminal-bench tasks, ctr-optimization and nextjs-performance are affected.

**Evidence bundle (C5/C8/C10).** `GET /submissions/{id}/evidence` (`routers/submissions.get_evidence_bundle`) returns one JSON file bundling the Docker build log, the Static Checks report and the Rubric Check report, plus `summary_markdown` (`submission_service.build_summary_markdown`): a README/summary template-filled straight from `SubmissionSchema` -- task name, checksum consistency (`ChecksumInfo`), every gate's status, agent trial pass rate and the full pass@k table, and total recorded `LlmSpend` for that submission. No LLM call renders it, so every field is a real value or an explicit "not run yet"/"not recorded", never a `[fill]` placeholder; extend that function, not a separate template file, when a deliverable needs another field. Before returning, the whole bundle passes through `submission_service.redact_host_paths`, which strips the username segment out of every absolute `/Users/<user>/...` or `/home/<user>/...` path (catches both this machine's own paths and ones baked into task file content from someone else's) -- applied only at this export boundary, never to data stored or shown inside the platform itself.

**4.1 categories (A to I).** All advisory; none changes a gate. *A (per-test results):* `verifier_report` also flags a score-details file whose own `reward`/`passed` disagrees with the reward (`_details_flags`), and `submission_service._verifier(run, expected_tests)` adds `count_flag` when a run's ctrf lists a different number of tests than the passing Oracle runs (`_expected_tests`, the most common count; shown as `OracleRunsResult.expected_tests`; not applied to Nop). The evidence download carries every run's report and sidecar in `verifier_reports`. *B (agent code in the grader):* `services/verifier_isolation.py` (in Static Checks) reads test.sh, tests/*.py and task.toml for the safe pattern: `verifier_reward_reset` warns in shared mode when test.sh never removes or writes `reward.json` (Harbor 0.23 reads reward.json before reward.txt, mounts /logs/verifier in the agent's container and only empties it in separate mode); `verifier_imports_agent_code` (sys.path/importlib/runpy on agent paths, PYTHONPATH, `python -m pytest` run from an agent-writable cwd in shared mode); `verifier_runs_agent_code` (subprocess argv or test.sh commands whose program is agent-written, root unless `user=`/setpriv/runuser/su/sudo -u; `pip install pytest==x` or `python /tests/x.py /app/out` do not count); `verifier_tests_readable` (agent code dropped to another user but no `chmod 700 /tests`); `verifier_evaluates_answer` (eval/sympify/pickle/yaml.load/torch.load); `verifier_inherited_pipe` (os.fork + os.pipe); result files under /tmp; seeds in input names; Lean keyword checks. `harbor_runner._parse_trial` adds `reward_file_flags` (reward.json/reward.txt on disk disagree with each other or with the recorded reward, read after the container is gone) and `harness_error_flags` (teardown errors, PermissionError, INTERNALERROR in test-stdout on a non-passing trial). Cheat Trials (B.2): `POST /cheat-trial?n=1..3&max_cost_usd=` replaces earlier rows and pre-creates n `cheat_trial` rows (run_index 0..n-1); one Harbor job runs them in sequence, each reward-1 trial gets its own `harbor analyze` check on `TrialOutcome.trial_dir`; `CheatTrialResult` keeps the first trial's fields for compatibility and adds `n`, `runs` and `summary` (trap held / solved honestly / reward hacking found / unresolved / inconclusive); status is failed if any trial needs a human. The cheat directives themselves are unchanged. *C (answer exposure):* `services/answer_exposure.py`, stage `answer_exposure` (`POST /answer-exposure`, no LLM/Docker): answer-like names and .git in environment/ and the image listing, exact copies of solution/ and tests/ files (an unchanged starter file at the same package path is info), and long numbers, hashes and long strings the tests compare against that also appear in agent-visible text (bare identifiers skipped). Noisy by design. 5.0 extras: `symlink_to_answer` (warn) and `symlink_in_environment` (info) for symlinks in environment/, `future_timestamp` and `old_timestamp` (info; a file over a year older than the rest of environment/), and `version_banner` (info; a commit/revision or a GitHub tree/blob/commit URL; 1 of 49 stored tasks). Extraction writes a symlink entry as a plain file and keeps no mtime, so `ziputil.safe_extract` records both in `zip_entries.json` beside the extraction folder (never inside the task) and `answer_exposure.scan` reads it; uploads from before it existed get the banner check only. *D/E:* the shared-first-failure note now says "possibly an over-strict grader … contested, needs a human"; Sufficiency adds `[formula]`; `POST /edge-cases?probe=true` (needs an Oracle pass) has the judge break the Oracle's answer on up to 4 uncovered cases (`variant_probe.propose_edge_breaks`) and runs each through `task_runner._run_variant` (shared with the two probes): `slipped_through` confirms the gap, `caught` removes the case from "uncovered". *F (agent-visible files):* after Build, `_record_image_inventory` runs `image_inventory.collect` (one `docker run --network none` of the built image: files under WORKDIR and /app, /workspace, /data, /home, /root, /srv, /opt, /mnt, /task with caches pruned, up to 5000, plus pip freeze, dpkg/apk and global npm) into a `image_inventory` Run (`POST /image-inventory` re-lists old builds). Sufficiency gets `judge_section`: environment/ files whose name and size are not in the image are listed as hidden (build-stage only), plus files the build created; `[invisible]` asks about rules only in README, solution/, tests/ or those files, and README.md is shown as hidden author notes. *G (flaky):* `OracleRunsResult.flaky`/`flaky_note` when finished runs mix 1 and 0, or a note to run 5 when Static Checks found timing or live-folder tests; `POST /oracle?stress=true` records `oracle_stress` runs (never in the gate, still in the checksum comparison) while `docker_orchestrator.start_cpu_load` runs a busy loop per CPU, capped at all CPUs but one (with every CPU taken, Docker Desktop's daemon in the same VM stopped answering Harbor), from a labelled sibling container of the task's own image (instead of a second parallel Harbor job, which this machine cannot run); `stress_note` compares them with the quiet runs. `services/reproducibility_checks.py` warns on wall-clock assertions, live-folder scans without FileNotFoundError handling, privilege drops without `cd`/`cwd=`, and notes a non-root image USER. Thread-pool pins are left to the vendored `check-cpu-threads`. *H (reproducibility):* `POST /fresh-build` (`run_fresh_build`, kind `fresh_build`): `docker build --no-cache --pull` into `taskeval/<id>:fresh` (removed afterwards), then one Oracle on a task copy where `harbor_runner._bust_build_cache` puts an ENV after every FROM so each RUN step fetches again (its checksum differs by design and is not compared). Static checks for pins without their dependencies (`transitive_pins`), every FROM and compose `image:` digest-pinned, run-time downloads in solve.sh and scripts the instruction names, and a separate verifier image lacking collected requirements or data the environment supplies. *I:* see TB Static Checks; when `check-task-fields` fails the output starts with the full expected `## Task Metadata` block (`tb_static_checks.expected_readme_metadata`) and any `REPLACE_WITH_` placeholders, which Static Checks also reports. On Windows the TB checks run with Git for Windows' bash (`_bash()`: a bare `bash` resolves to WSL's launcher, which cannot open Windows paths) and a directory junction instead of a symlink (which needs admin rights), removed before the temp dir is cleaned; a check whose tool is missing (`dockerfile-pin`) is `skipped`, not failed, and WARN lines of passing advisory checks are shown. The evidence bundle also has `run_limits` (agent timeout as applied, with a warning below 28800 s and when AGENT_TIMEOUT_SEC is unset, cpus, memory, platform, the latest trial's recorded facts), `oracle` (flaky and stress notes), `cheat_trial`, `answer_exposure`, `fresh_build` and `image_inventory`.

## Frontend

- File-based routing in `src/routes/` (`index.tsx` = submission list/upload, `submissions.$id.tsx` = stage dashboard, which polls with TanStack Query `refetchInterval` while stages run). `src/routeTree.gen.ts` is generated, so don't edit it. `__root.tsx` is the only root layout, so don't add Next.js/Remix-style `pages/` or `layout.tsx` files.
- `vite.config.ts` uses `@lovable.dev/vite-tanstack-config`, which already bundles the TanStack Start, React, Tailwind, tsconfig-paths and nitro plugins. Don't add them again, or you'll get duplicate plugins that break the build.
- `src/components/ui/` is generated shadcn/ui code. The `@/` alias maps to `src/`.
