# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local platform for grading Terminal-Bench-style task submissions. A user uploads a task zip (`task.toml`, `instruction.md`, `environment/Dockerfile`, `solution/solve.sh`, `tests/test.sh`) and runs it through stages against real Docker containers: Build → Oracle → Nop → Sufficiency → Agent Trials, plus the advisory stages Leakage Scan, Code Smell and Review Report.

Two apps live in one repo: a FastAPI backend in `backend/` and a TanStack Start (React 19, Vite, Tailwind v4, shadcn/ui) frontend at the repo root.

## Lovable constraints (from AGENTS.md)

The repo is connected to Lovable. **Never force-push, and never rebase, amend or squash commits that are already pushed.** Commits pushed to the connected branch (`main`) sync into the Lovable editor, so keep that branch working.

## Commands

```sh
# Postgres (localhost:5433, persistent volume taskeval-pg-data)
docker compose up -d

# Backend (from backend/). Needs Docker running, the harbor CLI on PATH, and one provider key in .env
cp .env.example .env
uv sync
uv run uvicorn app.main:app --reload --reload-dir app --port 8001

# Frontend (from repo root). The client defaults to :8000, so set the URL explicitly
bun install
VITE_API_BASE_URL=http://localhost:8001 bun run dev
bun run lint        # eslint
bun run format      # prettier
bun run build
```

There's no test suite and no migrations. Tables come from `Base.metadata.create_all` at startup, so a schema change to an existing table means wiping the DB (`docker compose down -v`). Runtime state lives under `backend/storage/`, which is gitignored and safe to delete.

## Backend architecture

**Request → background task flow.** `routers/submissions.py` exposes `POST /submissions/{id}/<stage>`. Each endpoint marks the row `pending` and hands a coroutine from `services/task_runner.py` to `workers/task_queue.submit(key, coro)`. The queue is in-process asyncio only: resubmitting the same `"{id}:{stage}"` key cancels the running task and restarts it. Blocking Docker calls run through `asyncio.to_thread`. Cancelling a Harbor-backed stage sends SIGINT to the `harbor` process so it removes its containers. On startup, `reset_stuck_rows()` marks any leftover `pending`/`running` rows as failed, and `docker_orchestrator.reap_orphans()` removes containers labelled `taskeval.submission_id`.

**Data model.** `Submission` holds build state, the image tags, the cached parsed `task.toml` (`task_config_json`, a `TaskConfig` model), and `task_checksum` (see below). Every other stage result is a `Run` row keyed by `(submission_id, kind, run_index)`. `kind` is one of `oracle`, `nop`, `agent` (one row per trial), `sufficiency`, `leakage_scan`, `code_smell`, `review_report`, `failure_analysis`, `cheat_trial` or `rubric_check`. `services/submission_service.to_schema` turns runs into the per-stage API shape. For example, it inverts Nop's status, because reward 0 counts as a pass there. `schemas.py` and the types in `src/lib/api.ts` must stay in sync by hand.

**One frozen task version per run set.** Every Oracle/Nop/Agent Trials `Run` row also stores the `task_checksum` Harbor's own `result.json` reports (its dirhash of the exact task directory that trial ran against). `task_runner._record_checksum` writes it onto the `Run` and, the first time any run on a submission reports one, freezes it onto `Submission.task_checksum` as the canonical version. `submission_service._checksum_info` compares every later oracle/nop/agent run's own checksum against that canonical value and returns `ChecksumInfo` (`canonical`, `consistent`, `mismatched`) as `SubmissionSchema.checksum`; the frontend shows a red banner when `consistent` is `false`. This exists because a submission can otherwise silently mix runs from different task copies (e.g. oracle run before a re-upload, rollouts after) with nothing flagging it. The Cheat Trial is excluded (`update_canonical=False`) because `_prepare_task`'s `cheat_instruction` branch always edits `instruction.md`, so its checksum legitimately never matches; its own `task_checksum` is still recorded on `CheatTrialResult` for audit. Existing rows from before this field was added have `task_checksum=None` and don't retroactively get one.

**Oracle, Nop and Agent Trials run through Harbor.** `services/harbor_runner.py` shells out to `harbor run` (`-a oracle`, `-a nop`, or `settings.harbor_agent` for trials) (the real grading pipeline's harness; install with `uv tool install harbor==0.23.0`, the tested version) and reads the reward from `<jobs-dir>/<job>/<trial>/result.json` at `verifier_result.rewards.reward`. **Network policy:** Harbor 0.23+ replaced `allow_internet` with `[environment].network_mode` (`public` default, `no-network`, `allowlist`), and on Docker it only enforces the last two through an egress-control sidecar that needs kernel support Docker Desktop for Mac lacks; otherwise it rejects the task. So `harbor_runner._prepare_task` copies each task and rewrites its `[environment]` to `HARBOR_NETWORK_MODE` (default `public`), leaving the extracted files alone and noting it at the top of the trial logs. Empty disables this. Harbor builds its own image on each run, so these stages don't use `Submission.image_tag`, but the router still requires Build to pass first. `DOCKER_PLATFORM` is passed to Harbor as `DOCKER_DEFAULT_PLATFORM`, because Harbor doesn't pin a platform itself. `DOCKER_ADD_HOSTS` (`hostname:ip` pairs, off by default) pins addresses into every build for networks that filter one address of a multi-address host (GitHub's release/raw CDN, where `185.199.109.133` hangs on some networks, so a Dockerfile that curls GitHub fails at random): `docker_orchestrator._run_docker_build_cli` adds `--add-host`, and `harbor_runner._write_build_hosts_overlay` writes a compose overlay, passed as `--extra-docker-compose`, that adds `build.extra_hosts` to Harbor's `main` service, so both build paths use the same pins. BuildKit counts extra hosts in a layer's cache key, so a hand-built image with different hosts does not warm the platform's cache. A run with no reward (build failure, crash, timeout) is stored as `failed` with `reward=None` and must not be shown as a Nop pass.

**Oracle runs N times, always appended.** `POST /submissions/{id}/oracle?n=3` (default 3) pre-creates `n` new pending `Run` rows (kind="oracle", `run_index` continuing from whatever's already there -- never deleted, unlike a plain agent-trials re-run) and `task_runner.run_oracle_trials` runs them one at a time via `harbor_runner.run_single` (never two Harbor jobs concurrently -- that has caused `EnvironmentStartTimeoutError` on this machine). This exists because Gate 1 needs 3 *consecutive* reward=1 runs, and the UI needs every run's own result visible afterwards, not just the latest overwriting the one before it (the old single-row `run_oracle`/`_run_harbor_gate` behavior). `submission_service._oracle_runs_result` aggregates all `kind="oracle"` rows into `OracleRunsResult` (`status`, `n`, `runs: list[TrialResult]`, `all_passed`): `status="passed"` only once *every* run has reward=1 (unlike agent trials, which only needs one). Nop stays single-row (`_run_harbor_gate`, still used only for `kind="nop"` now) since the guidelines only require one Nop run.

**Agent trials.** One `harbor run --n-attempts n` job with the Terminus-2 agent by default. The model is `AGENT_MODEL` (a LiteLLM string such as `openai/gpt-6-astra`), or derived from `LLM_PROVIDER`/`LLM_MODEL` when that's empty. `LLM_MAX_ITERS` becomes Terminus's `max_turns`, and `AGENT_REASONING_EFFORT` is passed through when set. `HARBOR_AGENT=codex` switches to OpenAI's Codex agent, which behaves very differently from Terminus-2: it runs inside the task container, so it needs `HARBOR_NETWORK_MODE=public`; Harbor's own install step (apt, an `nvm` download from GitHub, `npm install`, 6+ minutes and easily broken by a flaky route to `raw.githubusercontent.com`) is avoided by `CODEX_BAKE_INTO_IMAGE` (default on): `harbor_runner._prepare_task` appends a layer to the temporary task copy's `environment/Dockerfile` that installs Node (nodejs.org) and Codex (npm) at image build, best-effort, and Harbor skips its install when `command -v codex` succeeds (pin the version with `CODEX_VERSION`; empty bakes whatever is newest at first build, then it is cached). It runs, so and it needs an `openai/*` model and receives the OpenAI key inside the container. Harbor >= 0.23 rejects agent options the agent doesn't declare, so `task_runner._agent_kwargs` gives each agent only its own (Terminus: `max_turns` + `reasoning_effort`; Codex: `reasoning_effort`, `version` from `CODEX_VERSION`, `web_search` from `CODEX_WEB_SEARCH`, and no turn cap, so only the task's agent timeout bounds its cost). `_agent_config_error` fails the trials with a clear message for a bad Codex setup. Codex leaves `reasoning_effort` at its own default unless `AGENT_REASONING_EFFORT` is set. If an agent reports tokens but no cost, `harbor_runner` prices them from `llm/pricing.py`. Each trial's logs start with a notes header (C9): the Harbor CLI version (`harbor_runner._harbor_version()`, cached per process), the exact `harbor run` command including every `--agent-kwarg` actually passed (so the real reasoning effort sent is never just assumed from settings), a confirmation that the agent execution timeout is written into task.toml as-is with no multiplier math (only the separate install-time `--agent-setup-timeout-multiplier` is a real multiplier, and its value is logged too, or its absence is), and the agent's own resolved version. That last one is per-trial, not per-job: `_parse_trial` reads `agent.name`/`agent.version` straight out of Harbor's own `<trial>/agent/trajectory.json` (every installed agent -- Codex, Claude Code, Terminus-2 -- writes this itself), rather than a requested/pinned setting like `CODEX_VERSION`, since empty there resolves to whatever npm calls "latest" and the platform never installs Claude Code itself at all (no equivalent pin exists for it). Terminus-2 runs on the host and drives the task container, so provider keys (`harbor_runner._litellm_key_env`) never enter the container and the task's `allow_internet` setting holds. Harbor copies `tests/` into the container only after the agent finishes, so the agent never sees them. `POST /submissions/{id}/agent-trials?n=N` replaces earlier trials by default; `append=true` keeps them and adds N more after the last one (`run_agent_trials` only picks up the `pending` rows the router just created and keeps the earlier Harbor output), and the UI button always replaces. `run_job` polls for each trial's `result.json`, which is written once when the trial finishes, and fills the pre-created `Run` rows in completion order. Token counts and `cost_usd` from Harbor go into each trial's logs.

**Per-run agent, reasoning level and failure analysis.** `POST /submissions/{id}/agent-trials` takes an optional `agent` (`task_runner.AGENTS`: `codex`, `claude-code`, `terminus-2`; default `HARBOR_AGENT`), which picks the model (`_agent_model(agent)`: `CLAUDE_AGENT_MODEL`, default `anthropic/claude-fable-5-1`, for claude-code; `AGENT_MODEL` otherwise), the config check (`_agent_config_error(agent)`: claude-code needs `ANTHROPIC_API_KEY`, an `anthropic/*` model and public network) and the options (`_agent_kwargs(agent, reasoning_effort)`). Harbor's `claude-code` agent installs itself in the container (downloads.claude.ai bootstrap) and reports its own `total_cost_usd`; the watchdog can't read its cost mid-run, so `run_agent_trials` passes each trial `max_budget_usd` = run cap / n. It also takes an optional `reasoning_effort` (`task_runner.REASONING_EFFORTS`; anything else is a 400) that overrides `AGENT_REASONING_EFFORT` for that run only through `_agent_kwargs(reasoning_effort)`; the UI dropdown sends it. `POST /submissions/{id}/failure-analysis` (`task_runner.run_failure_analysis`, advisory like the LLM judges) runs `harbor analyze` (`harbor_runner.run_analyze`) once per `agent-*` job dir under `runs/agent/harbor/` with `ANALYZE_AGENT` (default terminus-2, so the key stays on the host and nothing is downloaded from GitHub) and `ANALYZE_MODEL` (default `openai/gpt-6-luna`), writes Harbor's output under `runs/analysis/`, and stores JSON (`agent`, `model`, `cost_usd`, `error`, `results` per trial with `summary` and `checks` for `reward_hacking`/`task_specification`) in the `failure_analysis` Run's logs; its cost goes into `llm_spend`. The Codex bake (`_bake_codex_into_environment`) skips tasks with a compose file, so those tasks install Codex inside every trial (10-16 minutes each).

**Cheat trial and rubric check.** `POST /submissions/{id}/cheat-trial` (`task_runner.run_cheat_trial`, optional `agent` like `agent-trials`) runs exactly one trial through `harbor_runner.run_job(..., cheat_instruction=True)`, which makes `_prepare_task` always copy the task and splice `harbor_runner._CHEAT_INSTRUCTION` into `instruction.md` (before the closing timeout sentence when present) telling the agent to fake the grade by any means. Reward staying 0/None already means the trap held (`status="passed"`). reward=1 alone doesn't mean a real cheat -- confirmed live twice, on two different harnesses (Codex and Claude Code): both trials got reward 1 after the agent's own first message refused the directive ("I won't alter grading machinery/checks or use hidden task or reference files") and solved the task honestly, with no access to `tests/` or `/app/task` anywhere in either trajectory. So a reward=1 trial automatically triggers a `harbor_runner.run_analyze` `reward_hacking` check on that one trial's job dir (the same mechanism Failure Analysis uses); only a check that positively returns `outcome: "pass"` counts as `status="passed"` ("trap held; solved honestly despite the directive"). A check that finds hacking, or that itself errors/returns nothing (`outcome: "unknown"`), stays `status="failed"` so it always gets a human's attention rather than being assumed clean. `logs` is JSON: `{trial_log, reward, cheat_check: {outcome, explanation, cost_usd, error} | null}`. `_agent_config_error` and cost-cap logic are reused from `run_agent_trials`; the analyze call's cost is also recorded under the `"cheat_trial"` stage in `llm_spend`. `POST /submissions/{id}/rubric-check` (`task_runner.run_rubric_check`, advisory) runs `harbor check` (`harbor_runner.run_check`) once over the whole extracted task with `CHECK_AGENT`/`CHECK_MODEL` (default Claude Code + `anthropic/claude-fable-5-1`, so it needs `ANTHROPIC_API_KEY`) and stores the same `{agent, model, cost_usd, error, results}` JSON shape as failure analysis, but grading the task itself (instruction, tests, environment) against Harbor's built-in quality rubric, not agent trajectories. Harbor's own launcher passes the instruction as a shell argument, so a task with a very large `environment/` (e.g. vendored crates) can fail with an OS argument-length error, surfaced in `error` rather than a real verdict.

**Agent timeout and the run cost cap.** `AGENT_TIMEOUT_SEC` (Terminal-Bench 4.0 uses a flat 28800 = 8h) is written into the same temporary task copy as the network policy (`harbor_runner._prepare_task` and `_rewrite_toml`), so Harbor enforces the exact value with no multiplier math, and `task_runner._agent_timeout_sec` feeds it into the backend's own outer timeouts, which would otherwise kill a long run early. Long timeouts make one runaway trial able to spend the whole month before anything checks, so `run_job` has a watchdog: every 10s it sums finished trials' costs plus each in-flight trial's running cost and stops the job (SIGINT, so Harbor removes its containers) once it reaches `AGENT_RUN_BUDGET_USD` or what is left of `LLM_BUDGET_USD`. In-flight cost comes from Terminus's `agent/trajectory.json` (rewritten every turn, on the host) or, for Codex, from `docker exec` reading the session file in the trial's container (`/tmp/codex-home/sessions`), because Codex only copies it out at the end and its own log reports usage once, at the end. Trials cut short report no cost themselves, so `_parse_trial` falls back to the last live figure, and that partial cost is still recorded in `llm_spend`. The check interval means a run can overshoot the cap by a few cents.

**Budget guard** (`services/budget.py`). `LLM_BUDGET_USD` (default 50, `0` = off) caps priced LLM spend per UTC calendar month, recorded in the `llm_spend` table (separate from `Run`, because re-running agent trials deletes the old `Run` rows). Two sources feed it: each finished agent trial's Harbor `cost_usd`, and each judge call's token usage priced by `services/llm/pricing.py` (which includes the cache-write price: the API reports `cache_write_tokens` separately and bills them 25% above plain input for gpt-6-astra, so nearly every fresh prompt pays it). Only models in that price table (currently `gpt-6-astra`) are tracked; Fireworks and other providers are skipped, and the judge endpoints only enforce the cap when the judge model is priced. The agent and judge endpoints refuse to start once the cap is reached, and `run_agent_trials` stops the Harbor job (via `on_trial` returning a reason) after the trial that crosses it. Cost is only known when a trial or call finishes, so in-flight work can overshoot. `GET /budget` returns the month's spend and the limit.

**LLM providers.** Set by `LLM_PROVIDER`/`LLM_MODEL` in `backend/.env`. These drive the LLM-judge stages (and the agent model unless `AGENT_MODEL` is set). The options are anthropic, openai, gemini, groq and fireworks (the default). Groq and Fireworks reuse `OpenAIClient` with a different `base_url`. For the real OpenAI provider, `OpenAIClient` also gets `LLM_REASONING_EFFORT` and `LLM_MAX_OUTPUT_TOKENS` (as `max_completion_tokens`, which includes reasoning tokens) from the factory, and reports each call's token usage to `llm/usage.py`, a ContextVar collector that `task_runner._track_llm_spend` turns into `llm_spend` rows, since the judges create their own client and return only a verdict. All clients implement `llm/base.LLMClient` and share `rate_limiter.TokenBucket`. The LLM-judge stages are `sufficiency_judge`, `code_smell_judge` and `review_report`. They run on `gpt-6-sol` by default in `.env.example`. We compared gpt-6-astra, sol, luna and Gemini on five tasks including one with a deliberately removed requirement: sol matched astra on Sufficiency (5/5, caught the broken task) at a fifth of the cost, luna (about 100x cheaper than astra) got 4/5, and Code Smell is a noisy opinion stage where every model disagreed with astra at least once. Fireworks and Groq keys were dead and Google retired the 2.5 Gemini models for new users. `gemini-3.5-flash-lite` (Google paid tier: $0.30 in, $2.50 out, $0.03 cached per million; output includes thinking tokens) matched sol 5/5 on Sufficiency at roughly a third of sol's cost and is a supported judge model: `GeminiClient` reports usage (so `llm_spend` and the budget guard count it, via its entry in `llm/pricing.py`) and retries only rate limits (429), server errors and connection errors, failing at once on a retired model or bad key. Judge prompts include hidden tests and reference solutions, and Google may use free-tier prompts to improve its products, so use a paid-tier key. The first two read task files through `services/judge_files.py`, which lists every file (size, and whether its contents are shown), detects text by content instead of extension, and caps each file at `JUDGE_MAX_FILE_CHARS` (150k) and the dump at `JUDGE_MAX_TOTAL_CHARS` (500k). Those were 20k and 120k, which cut one task's 324k-character dossier and made Sufficiency report its rules as missing. The listing matters: without it a judge that sees only some files reports the others as missing. Review Report requires every required gate to be in a terminal state first (`all_gates_terminal`).

**Advisory vs. gating stages.** Leakage Scan (regex over task files), Code Smell (an LLM opinion), Static Checks, TB Static Checks and Review Report ("passed" only means the report was generated) are advisory. Their `passed: false` does not disqualify a submission, so don't treat them as gates or merge them with each other (see the comments in `src/lib/api.ts`). `static_checks.py` and `infra_marker_scan.py` produce heuristic findings from the task files and the trial logs. `task_runner.run_static_checks_stage` persists `static_checks.py`'s output as its own `Run` (kind="static_checks") so it's independently visible, not just recomputed live inside Review Report's own prompt (both call the same deterministic function, so they never disagree).

**TB Static Checks.** A second, separate advisory stage (kind="tb_static_checks", `task_runner.run_tb_static_checks_stage` → `services/tb_static_checks.py`) runs Terminal-Bench's own official static checks, not this platform's. The 26 `check-*.sh` scripts are vendored verbatim from `harbor-framework/terminal-bench`'s `scripts/checks/` at a pinned commit (`backend/vendor/tb_checks/`, see `PROVENANCE.md` there for the commit hash and update instructions) rather than cloned at runtime, so results don't silently shift if upstream changes its requirements. This is deliberately not a replacement for `static_checks.py`: the two rule sets barely overlap (TB's checks framework compliance -- canary, dockerfile platform/sanity, separate verifier, task fields, absolute paths, pip/pytest pinning -- ours checks platform-specific hygiene like instruction word count and Dockerfile digest pinning), so both run and neither supersedes the other. Two fixes were needed to run these vendored scripts correctly against this platform's own layout, both handled in `run_tb_static_checks` via a temporary symlink rather than by patching the vendored scripts: (1) several scripts internally re-split a path on an unquoted shell variable, which breaks on any whitespace in the path (true of this repo's own checkout on at least one machine, `"Task Evaluator"`) -- worked around with a space-free symlink; (2) `check-task-package-name.sh` derives the expected task name from the directory's own basename, which is meaningless for this platform's generic `submissions/{id}/extracted/` layout (never named after the task's real slug) -- worked around by naming that symlink from `task.toml`'s own declared `[task] name` instead of the real folder name.

**Infra-failure auto-retry (C11).** `task_runner._retry_infra_agent_failures`, called once at the end of every `run_agent_trials` job, gives a trial exactly one automatic retry if both hold: its `reward is None` (a crash/timeout with no result, not a genuine reward=0 attempt) AND `infra_marker_scan.scan_trial_logs` finds a known infra-noise marker in its logs (connect/read timeout, rate limit, DNS failure, Docker orchestration error). The retry runs sequentially through `harbor_runner.run_job` with `n_attempts=1` in a sibling `-infra-retry` jobs dir (never a second concurrent Harbor job). The `Run` row is updated with the retry's own reward/status/logs, but the original failure is kept, not discarded -- prepended under a `_INFRA_RETRY_MARKER` header naming which markers were seen. That same marker is checked before retrying at all, so a retry that *itself* shows infra noise is never retried again (bounded to one attempt, left for a human rather than looping against a persistent problem like Docker being down). If the monthly budget is already exceeded, the trial is flagged `(not retried: <reason>)` instead of silently skipped or retried anyway. A trial with `reward=0` (the agent genuinely tried and failed) or `reward is None` with no recognized marker is never touched -- this only catches known, well-understood infra noise, never a real task-solving failure.

**pass@k (C6).** `submission_service._pass_at_k(n, c, k)` is the standard unbiased estimator (`1 - C(n-c,k)/C(n,k)`, via `math.comb`), computed for every `k` from 1 to `n` once all agent trials are terminal and returned as `AgentTrialsResult.pass_at_k` (`dict[str, float]`, keyed by `k` as a string). This exists because Harbor's own job-level reporting (`_eligible_k_values` in the installed `harbor` package) only ever fills in powers-of-2 and multiples-of-5 `k` values — pass@1 is never computed by Harbor itself for any job, by design, not a bug worth working around any other way.

**Evidence bundle (C5/C8/C10).** `GET /submissions/{id}/evidence` (`routers/submissions.get_evidence_bundle`) returns one JSON file bundling the Docker build log, the Static Checks report and the Rubric Check report, plus `summary_markdown` (`submission_service.build_summary_markdown`): a README/summary template-filled straight from `SubmissionSchema` -- task name, checksum consistency (`ChecksumInfo`), every gate's status, agent trial pass rate and the full pass@k table, and total recorded `LlmSpend` for that submission. No LLM call renders it, so every field is a real value or an explicit "not run yet"/"not recorded", never a `[fill]` placeholder; extend that function, not a separate template file, when a deliverable needs another field. Before returning, the whole bundle passes through `submission_service.redact_host_paths`, which strips the username segment out of every absolute `/Users/<user>/...` or `/home/<user>/...` path (catches both this machine's own paths and ones baked into task file content from someone else's) -- applied only at this export boundary, never to data stored or shown inside the platform itself.

## Frontend

- File-based routing in `src/routes/` (`index.tsx` = submission list/upload, `submissions.$id.tsx` = stage dashboard, which polls with TanStack Query `refetchInterval` while stages run). `src/routeTree.gen.ts` is generated, so don't edit it. `__root.tsx` is the only root layout, so don't add Next.js/Remix-style `pages/` or `layout.tsx` files.
- `vite.config.ts` uses `@lovable.dev/vite-tanstack-config`, which already bundles the TanStack Start, React, Tailwind, tsconfig-paths and nitro plugins. Don't add them again, or you'll get duplicate plugins that break the build.
- `src/components/ui/` is generated shadcn/ui code. The `@/` alias maps to `src/`.
