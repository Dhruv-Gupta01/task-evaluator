# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local platform for grading Terminal-Bench-style task submissions. A user uploads a task zip (`task.toml`, `instruction.md`, `environment/Dockerfile`, `solution/solve.sh`, `tests/test.sh`) and runs it through stages against real Docker containers: Build → Oracle → Nop → Sufficiency → Agent Trials, plus the advisory stages Leakage Scan and Review Report.

Two apps live in one repo: a FastAPI backend in `backend/` and a TanStack Start (React 19, Vite, Tailwind v4, shadcn/ui) frontend at the repo root.

## Lovable constraints (from AGENTS.md)

The repo is connected to Lovable. **Never force-push, and never rebase, amend or squash commits that are already pushed.** Commits pushed to the connected branch (`main`) sync into the Lovable editor, so keep that branch working.

```sh

docker compose up -d

# Backend (from backend/). Needs Docker running, the harbor CLI on PATH, and one provider key in .env
cp .env.example .env

uv run uvicorn app.main:app --reload --reload-dir app --port 8001

# Frontend (from repo root). The client defaults to :8000, so set the URL explicitly
bun install
VITE_API_BASE_URL=http://localhost:8001 bun run dev
bun run lint        # eslint
bun run format      # prettier
bun run build
```

Unit tests live in `backend/tests/` (from `backend/`: `uv run --with pytest --with httpx pytest`; no DB or Docker needed). There are no migrations. Tables come from `Base.metadata.create_all` at startup, so a schema change to an existing table means wiping the DB (`docker compose down -v`). Runtime state lives under `backend/storage/`, which is gitignored and safe to delete.

## Scripts, docs and secrets

- `backend/scripts/` holds standalone tools, run from `backend/` against a running backend or the DB: `run_tb_test.py` (runs stages on one real Terminal-Bench task and writes evidence under `docs/testing/<version>/`; `.claude/run_*.sh` are the batch drivers), `export_evidence.py` (rebuilds a `docs/testing/` entry from the DB), `diff_vendored_checks.py` (upstream vs vendored checks), and `log_issue.py` / `log_cost.py` (append rows to the TB Milestone Issue Log Google Sheet via `uv run --with gspread python backend/scripts/<name>.py ...`; `log_cost.py` reads the UI's evidence download).
- `docs/HANDOVER.md` is the operator/maintainer overview (architecture, costs, known issues, day-to-day operation); read it before large changes. `docs/testing/` is the real-task test evidence. The `task-deliverable` skill builds the client evidence package.
- The Google service-account key (`platinum-voice-*.json` in the repo root) and `.env` are gitignored credentials. Never commit, print or paste them.
- There is no Python lint or test config in `backend/pyproject.toml`; the frontend `bun run lint` is the only linter.

## Backend architecture

**Request → background task flow.** `routers/submissions.py` exposes `POST /submissions/{id}/<stage>`. Each endpoint marks the row `pending` and hands a coroutine from `services/task_runner.py` to `workers/task_queue.submit(key, coro)`. The queue is in-process asyncio only: resubmitting the same `"{id}:{stage}"` key cancels the running task and restarts it. Blocking Docker calls run through `asyncio.to_thread`. Cancelling a Harbor-backed stage sends SIGINT to the `harbor` process so it removes its containers. On startup, `reset_stuck_rows()` marks any leftover `pending`/`running` rows as failed, and `docker_orchestrator.reap_orphans()` removes containers labelled `taskeval.submission_id`.

**Data model.** `Submission` holds build state, the image tags, the cached parsed `task.toml` (`task_config_json`, a `TaskConfig` model), and `task_checksum` (see below). Every other stage result is a `Run` row keyed by `(submission_id, kind, run_index)`. `kind` is one of `oracle`, `oracle_stress`, `nop`, `agent` (one row per trial), `sufficiency`, `leakage_scan`, `review_report`, `failure_analysis`, `cheat_trial` (one row per trial), `rubric_check`, `static_checks`, `tb_static_checks`, `ai_detection`, `variant_probe`, `weak_probe`, `edge_cases`, `reviewer_decision`, `tier0_decision`, `tier1_loop`, `tier1_decision`, `answer_exposure`, `image_inventory`, `fresh_build`, `tier0_probes`, `tier2_loop` or `tier2_decision`. `services/submission_service.to_schema` turns runs into the per-stage API shape. For example, it inverts Nop's status, because reward 0 counts as a pass there. `schemas.py` and the types in `src/lib/api.ts` must stay in sync by hand.

**One frozen task version per run set.** Every Oracle/Nop/Agent Trials `Run` row also stores the `task_checksum` Harbor's own `result.json` reports (its dirhash of the exact task directory that trial ran against). `task_runner._record_checksum` writes it onto the `Run` and, the first time any run on a submission reports one, freezes it onto `Submission.task_checksum` as the canonical version. `submission_service._checksum_info` compares every later oracle/nop/agent run's own checksum against that canonical value and returns `ChecksumInfo` (`canonical`, `consistent`, `mismatched`) as `SubmissionSchema.checksum`; the frontend shows a red banner when `consistent` is `false`. This exists because a submission can otherwise silently mix runs from different task copies (e.g. oracle run before a re-upload, rollouts after) with nothing flagging it. The Cheat Trial is excluded (`update_canonical=False`) because `_prepare_task`'s `cheat_instruction` branch always edits `instruction.md`, so its checksum legitimately never matches; its own `task_checksum` is still recorded on `CheatTrialResult` for audit. Existing rows from before this field was added have `task_checksum=None` and don't retroactively get one. Trials whose logs carry `harbor_runner.CODEX_BAKE_NOTE_MARKER` (Codex baked into the task copy's Dockerfile, which changes Harbor's checksum by design) are left out of the comparison and listed in `ChecksumInfo.not_comparable`, and never set the canonical checksum; a real mismatch among the other runs is still flagged.

**Oracle, Nop and Agent Trials run through Harbor.** `services/harbor_runner.py` shells out to `harbor run` (`-a oracle`, `-a nop`, or `settings.harbor_agent` for trials) (the real grading pipeline's harness; install with `uv tool install harbor==0.26.0`, the tested version) and reads the reward from `<jobs-dir>/<job>/<trial>/result.json` at `verifier_result.rewards.reward`. **Network policy:** Harbor 0.23+ replaced `allow_internet` with `[environment].network_mode` (`public` default, `no-network`, `allowlist`), and on Docker it only enforces the last two through an egress-control sidecar that needs kernel support Docker Desktop for Mac lacks; otherwise it rejects the task. So `harbor_runner._prepare_task` copies each task and rewrites its `[environment]` to `HARBOR_NETWORK_MODE` (default `public`), leaving the extracted files alone and noting it at the top of the trial logs. Empty disables this. On Windows `harbor_runner._new_group` starts Harbor in its own process group and `_stop` sends it Ctrl+Break (Windows cannot send SIGINT to another process), then `taskkill /T /F`; `.gitattributes` keeps `.sh`, Dockerfiles and the like on LF so a Windows checkout does not break them. Not yet run on a Windows machine. Harbor builds its own image on each run, so these stages don't use `Submission.image_tag`, but the router still requires Build to pass first. `DOCKER_PLATFORM` is passed to Harbor as `DOCKER_DEFAULT_PLATFORM`, because Harbor doesn't pin a platform itself. `DOCKER_ADD_HOSTS` (`hostname:ip` pairs, off by default) pins addresses into every build for networks that filter one address of a multi-address host (GitHub's release/raw CDN, where `185.199.109.133` hangs on some networks, so a Dockerfile that curls GitHub fails at random): `docker_orchestrator._run_docker_build_cli` adds `--add-host`, and `harbor_runner._write_build_hosts_overlay` writes a compose overlay, passed as `--extra-docker-compose`, that adds `build.extra_hosts` to Harbor's `main` service, so both build paths use the same pins. BuildKit counts extra hosts in a layer's cache key, so a hand-built image with different hosts does not warm the platform's cache. A run with no reward (build failure, crash, timeout) is stored as `failed` with `reward=None` and must not be shown as a Nop pass.

**Oracle runs N times, always appended.** `POST /submissions/{id}/oracle?n=3` (default 3) pre-creates `n` new pending `Run` rows (kind="oracle", `run_index` continuing from whatever's already there -- never deleted, unlike a plain agent-trials re-run) and `task_runner.run_oracle_trials` runs them one at a time via `harbor_runner.run_single` (never two Harbor jobs concurrently -- that has caused `EnvironmentStartTimeoutError` on this machine). This exists because Gate 1 needs 3 _consecutive_ reward=1 runs, and the UI needs every run's own result visible afterwards, not just the latest overwriting the one before it (the old single-row `run_oracle`/`_run_harbor_gate` behavior). `submission_service._oracle_runs_result` aggregates all `kind="oracle"` rows into `OracleRunsResult` (`status`, `n`, `runs: list[TrialResult]`, `all_passed`): `status="passed"` only once _every_ run has reward=1 (unlike agent trials, which only needs one). Nop stays single-row (`_run_harbor_gate`, still used only for `kind="nop"` now) since the guidelines only require one Nop run.

**Agent trials.** One `harbor run --n-attempts n` job with the Terminus-2 agent by default. The model is `AGENT_MODEL` (a LiteLLM string such as `openai/gpt-6-astra`), or derived from `LLM_PROVIDER`/`LLM_MODEL` when that's empty. `LLM_MAX_ITERS` becomes Terminus's `max_turns`, and `AGENT_REASONING_EFFORT` is passed through when set. `HARBOR_AGENT=codex` switches to OpenAI's Codex agent, which behaves very differently from Terminus-2: it runs inside the task container, so it needs `HARBOR_NETWORK_MODE=public`; Harbor's own install step (apt, an `nvm` download from GitHub, `npm install`, 6+ minutes and easily broken by a flaky route to `raw.githubusercontent.com`) is avoided by `CODEX_BAKE_INTO_IMAGE` (default on): `harbor_runner._prepare_task` appends a layer to the temporary task copy's `environment/Dockerfile` that installs Node (nodejs.org) and Codex (npm) at image build, best-effort, and Harbor skips its install when `command -v codex` succeeds (pin the version with `CODEX_VERSION`; empty bakes whatever is newest at first build). With `CODEX_VERSION` empty, `_bake_codex_into_environment` also stamps today's date into the install layer's own `RUN` line (`RUN echo "codex latest cache-bust: <date>" > /dev/null`, right before the real install command), because Docker's build cache would otherwise mean "latest" only ever means "whatever was newest the first time this task's image was built," silently frozen from then on -- a real risk distinct from (and in addition to) the actual incident this project hit, where `CODEX_VERSION` got pinned by a stray shell environment variable outside `.env`. The date line changes that layer's cache key once a day, which chains to the real install layer rebuilding fresh too. Never added when a version is pinned -- that's a deliberate choice, not staleness. It runs, so and it needs an `openai/*` model and receives the OpenAI key inside the container. Harbor >= 0.23 rejects agent options the agent doesn't declare, so `task_runner._agent_kwargs` gives each agent only its own (Terminus: `max_turns` + `reasoning_effort`; Codex: `reasoning_effort`, `version` from `CODEX_VERSION`, `web_search` from `CODEX_WEB_SEARCH`, and no turn cap, so only the task's agent timeout bounds its cost). `_agent_config_error` fails the trials with a clear message for a bad Codex setup. Codex leaves `reasoning_effort` at its own default unless `AGENT_REASONING_EFFORT` is set. If an agent reports tokens but no cost, `harbor_runner` prices them from `llm/pricing.py`. Each trial's logs start with a notes header (C9): the Harbor CLI version (`harbor_runner._harbor_version()`, cached per process), the exact `harbor run` command including every `--agent-kwarg` actually passed (so the real reasoning effort sent is never just assumed from settings), a confirmation that the agent execution timeout is written into task.toml as-is with no multiplier math (only the separate install-time `--agent-setup-timeout-multiplier` is a real multiplier, and its value is logged too, or its absence is), and the agent's own resolved version. That last one is per-trial, not per-job: `_parse_trial` reads `agent.name`/`agent.version` straight out of Harbor's own `<trial>/agent/trajectory.json` (every installed agent -- Codex, Claude Code, Terminus-2 -- writes this itself), rather than a requested/pinned setting like `CODEX_VERSION`, since empty there resolves to whatever npm calls "latest" and the platform never installs Claude Code itself at all (no equivalent pin exists for it). Terminus-2 runs on the host and drives the task container, so provider keys (`harbor_runner._litellm_key_env`) never enter the container and the task's `allow_internet` setting holds. Harbor copies `tests/` into the container only after the agent finishes, so the agent never sees them. `POST /submissions/{id}/agent-trials?n=N` replaces earlier trials by default; `append=true` keeps them and adds N more after the last one (`run_agent_trials` only picks up the `pending` rows the router just created and keeps the earlier Harbor output), and the UI button always replaces. `run_job` polls for each trial's `result.json`, which is written once when the trial finishes, and fills the pre-created `Run` rows in completion order. Token counts and `cost_usd` from Harbor go into each trial's logs. *Web tools off:* `AGENT_DISABLE_WEB_SEARCH` (default true) makes `task_runner._agent_kwargs` pass `disable_web_search=true` to Claude Code and Codex (`WEB_SEARCH_AGENTS`), which Harbor 0.25.0 and 0.26.0 turn into `--disallowedTools WebSearch,WebFetch` (Claude Code) or Codex's search setting, so an agent on the open network cannot look the answer up through its built-in tools. It reaches agent trials, the evidence sets, the cheat trial and Tier 1 and Tier 2, since all call `_agent_kwargs`. Terminus-2 has no such tools and Harbor rejects an option an agent does not declare, so it gets none; an explicit `CODEX_WEB_SEARCH` wins for Codex; the analysis and rubric-check evaluators (`_evaluator_kwargs`) are not covered. It does **not** stop `curl`, `pip` or any other command in the container: only a restricted network does, and `HARBOR_NETWORK_MODE=public` is forced because Docker Desktop for Mac cannot enforce one, so `run_limits` in the evidence says trials ran with open internet and whether the web tools were off (`web_search_disabled`). Verified live on the smoke task with Claude Code on Haiku 4.5 (medium): the command logged `--disallowedTools WebSearch,WebFetch` and the agent's tool list had no web tool.

**Per-run agent, reasoning level and failure analysis.** `POST /submissions/{id}/agent-trials` takes an optional `agent` (`task_runner.AGENTS`: `codex`, `claude-code`, `terminus-2`; default `HARBOR_AGENT`) and an optional `model` (`valid_model_override` checks the provider prefix; the UI's Model dropdown on the Agent Trials card), which pick the model (`_agent_model(agent, model)`: the override, else `CLAUDE_AGENT_MODEL`, default `anthropic/claude-fable-5-1`, for claude-code, else `AGENT_MODEL`), the config check (`_agent_config_error(agent)`: claude-code needs `ANTHROPIC_API_KEY`, an `anthropic/*` model and public network) and the options (`_agent_kwargs(agent, reasoning_effort)`). Harbor's `claude-code` agent installs itself in the container (downloads.claude.ai bootstrap) and reports its own `total_cost_usd`; the watchdog can't read its cost mid-run, so `run_agent_trials` passes each trial `max_budget_usd` = run cap / n. It also takes an optional `reasoning_effort` (`task_runner.REASONING_EFFORTS`; anything else is a 400) that overrides `AGENT_REASONING_EFFORT` for that run only through `_agent_kwargs(reasoning_effort)`; the UI dropdown sends it. `POST /submissions/{id}/failure-analysis` (`task_runner.run_failure_analysis`, advisory like the LLM judges) runs `harbor analyze` (`harbor_runner.run_analyze`) once per `agent-*` job dir under `runs/agent/harbor/` with `ANALYZE_AGENT` (default terminus-2, so the key stays on the host and nothing is downloaded from GitHub) and `ANALYZE_MODEL` (default `openai/gpt-6-luna`), writes Harbor's output under `runs/analysis/`, and stores JSON (`agent`, `model`, `cost_usd`, `error`, `results` per trial with `summary` and `checks` for `reward_hacking`/`task_specification`) in the `failure_analysis` Run's logs; its cost goes into `llm_spend`. The Codex bake (`_bake_codex_into_environment`) skips a task only when a compose file in `environment/` gives the `main` service its own `build:` or `image:` (`_compose_replaces_main_image`; an unparseable file also skips), because then the agent's container may not come from `environment/Dockerfile`; those tasks install Codex inside every trial (10-16 minutes each). A compose file that only adds other services or `depends_on` (e.g. int8-runtime-port) is baked as normal, since Harbor's own base compose builds `main` from `environment/`.

**Cheat trial and rubric check.** `POST /submissions/{id}/cheat-trial` (`task_runner.run_cheat_trial`, optional `agent`, `reasoning_effort` and `model` like `agent-trials`; `model` overrides the agent's `.env` model for that run only (`_agent_model(agent, model)`; `valid_model_override` 400s a malformed string or the wrong provider, since Codex runs only `openai/*` and Claude Code only `anthropic/*`, and any model with the right prefix is accepted); `GET /agent-models` lists the choices the UI offers (`MODEL_CHOICES`, `.env` model first). The UI's Model and Reasoning dropdowns default to "Same as Agent Trials", i.e. whatever agent, model (including its Model dropdown) and reasoning the Agent Trials card has selected, so a cheat trial run at a low `AGENT_REASONING_EFFORT` is a weaker test: pick max for a stricter one) runs 1 to 3 trials (`n`, see 4.1 B.2 below) in one job through `harbor_runner.run_job(..., cheat_instruction=True)`, which makes `_prepare_task` always copy the task and splice `harbor_runner._CHEAT_INSTRUCTION` into `instruction.md` (before the closing timeout sentence when present) telling the agent to fake the grade by any means. Reward staying 0/None already means the trap held (`status="passed"`). reward=1 alone doesn't mean a real cheat -- confirmed live twice, on two different harnesses (Codex and Claude Code): both trials got reward 1 after the agent's own first message refused the directive ("I won't alter grading machinery/checks or use hidden task or reference files") and solved the task honestly, with no access to `tests/` or `/app/task` anywhere in either trajectory. So a reward=1 trial automatically triggers a `harbor_runner.run_analyze` `reward_hacking` check on that one trial's job dir (the same mechanism Failure Analysis uses); only a check that positively returns `outcome: "pass"` counts as `status="passed"` ("trap held; solved honestly despite the directive"). A check that finds hacking, or that itself errors/returns nothing (`outcome: "unknown"`), stays `status="failed"` so it always gets a human's attention rather than being assumed clean. `logs` is JSON: `{trial_log, reward, cheat_check: {outcome, explanation, cost_usd, error} | null, cheat_prompt}`. `cheat_prompt="tb"` splices in `vendor/tb_prompts/hack-trial-prompt.md` (a more aggressive, explicit red-team-style directive) instead of the platform's own `_CHEAT_INSTRUCTION`, via `harbor_runner._prepare_task`'s new `cheat_instruction_text` param. `_agent_config_error` and cost-cap logic are reused from `run_agent_trials`; the analyze call's cost is also recorded under the `"cheat_trial"` stage in `llm_spend`. `POST /submissions/{id}/rubric-check` (`task_runner.run_rubric_check`, advisory, optional `rubric`) runs `harbor check` (`harbor_runner.run_check`) once over the whole extracted task with `CHECK_AGENT`/`CHECK_MODEL` (default Claude Code + `anthropic/claude-fable-5-1`, so it needs `ANTHROPIC_API_KEY`) and stores the same `{agent, model, cost_usd, error, results, rubric}` JSON shape as failure analysis, plus `rubric_info` (TB only: `vendor_info.rubric_info()`, the criteria count read from the file, the upstream commit, its age and the drift reminder), but grading the task itself (instruction, tests, environment) against a rubric -- the vendored `rubric="tb"` by default since 4.1 (Harbor's built-in one with `rubric="default"`), from `vendor/tb_prompts/task-implementation.toml` -- not agent trajectories. Harbor's own launcher passes the instruction as a shell argument, so a task with a very large `environment/` (e.g. vendored crates) can fail with an OS argument-length error, surfaced in `error` rather than a real verdict.

**Vendored Terminal-Bench prompts (`backend/vendor/tb_prompts/`, see `PROVENANCE.md` there).** Five files copied verbatim from `harbor-framework/terminal-bench`'s `docs/prompts/` at a pinned commit, each an optional, richer alternative to a Harbor default -- never the default itself: `trial-analysis.toml` (6-criterion `harbor analyze -r` rubric: `task_specification`, `reward_hacking`, `difficulty_crux`, `near_miss`, `refusals`, `low_timeout`, vs. Harbor's own 2), `trial-analysis.txt` (the matching per-trial `-p` prompt), `trial-analysis-job.txt` (a job-*summary* prompt with a `{trial_results}` placeholder -- not a Harbor CLI flag, since Harbor has no built-in job-summary step; `task_runner.run_failure_analysis` does one extra LLM call with this template, substituting in that run's own results, only when `rubric="tb"`), `task-implementation.toml` (the TB `harbor check -r` rubric; the 2026-10-15 refresh added `effective_instruction_length`; Harbor's own has 11). `services/vendor_info.py` (K12) reads the criteria count, the check-script count and the pinned commit and date from these files, so no count is hard-coded; once the commit is older than `VENDOR_STALE_DAYS` (default 30, 0 = off) the TB Static Checks and Rubric Check results carry `stale` and a reminder to run `scripts/diff_vendored_checks.py`, shown in amber on both cards, and `hack-trial-prompt.md` (the Cheat Trial's alternate, more aggressive directive). `harbor_runner.run_analyze`/`run_check` both gained optional `rubric_path`/`prompt_path` params (`--rubric`/`--prompt` flags Harbor's CLI already supported but this platform never exposed) to use these. `task_runner.RUBRICS`/`CHEAT_PROMPTS` (`("default", "tb")`) are the only accepted values; the router validates and 400s on anything else.

**Agent timeout and the run cost cap.** `AGENT_TIMEOUT_SEC` (Terminal-Bench 4.0 uses a flat 28800 = 8h) is written into the same temporary task copy as the network policy (`harbor_runner._prepare_task` and `_rewrite_toml`), so Harbor enforces the exact value with no multiplier math, and `task_runner._agent_timeout_sec` feeds it into the backend's own outer timeouts, which would otherwise kill a long run early. Long timeouts make one runaway trial able to spend the whole month before anything checks, so `run_job` has a watchdog: every 10s it sums finished trials' costs plus each in-flight trial's running cost and stops the job (SIGINT, so Harbor removes its containers) once it reaches `AGENT_RUN_BUDGET_USD` or what is left of `LLM_BUDGET_USD`. In-flight cost comes from Terminus's `agent/trajectory.json` (rewritten every turn, on the host) or, for Codex, from `docker exec` reading the session file in the trial's container (`/tmp/codex-home/sessions`), because Codex only copies it out at the end and its own log reports usage once, at the end. Trials cut short report no cost themselves, so `_parse_trial` falls back to the last live figure, and that partial cost is still recorded in `llm_spend`. The check interval means a run can overshoot the cap by a few cents.

**Budget guard** (`services/budget.py`). `LLM_BUDGET_USD` (default 50, `0` = off) caps priced LLM spend per UTC calendar month, recorded in the `llm_spend` table (separate from `Run`, because re-running agent trials deletes the old `Run` rows). Two sources feed it: each finished agent trial's Harbor `cost_usd`, and each judge call's token usage priced by `services/llm/pricing.py` (which includes the cache-write price: the API reports `cache_write_tokens` separately and bills them 25% above plain input for gpt-6-astra, so nearly every fresh prompt pays it). Only models in that price table (currently `gpt-6-astra`) are tracked; Fireworks and other providers are skipped, and the judge endpoints only enforce the cap when the judge model is priced. The agent and judge endpoints refuse to start once the cap is reached, and `run_agent_trials` stops the Harbor job (via `on_trial` returning a reason) after the trial that crosses it. Cost is only known when a trial or call finishes, so in-flight work can overshoot. `GET /budget` returns the month's spend and the limit.

**LLM providers.** Set by `LLM_PROVIDER`/`LLM_MODEL` in `backend/.env`. These drive the LLM-judge stages (and the agent model unless `AGENT_MODEL` is set). The options are anthropic, openai, gemini, groq and fireworks (the default). Groq and Fireworks reuse `OpenAIClient` with a different `base_url`. For the real OpenAI provider, `OpenAIClient` also gets `LLM_REASONING_EFFORT` and `LLM_MAX_OUTPUT_TOKENS` (as `max_completion_tokens`, which includes reasoning tokens; default 0 = no cap, since a 16000 cap left the edge-case probe's long answer empty; Anthropic's API needs a cap, so 0 there means 16000) from the factory, and reports each call's token usage to `llm/usage.py`, a ContextVar collector that `task_runner._track_llm_spend` turns into `llm_spend` rows, since the judges create their own client and return only a verdict. All clients implement `llm/base.LLMClient` and share `rate_limiter.TokenBucket`. The LLM-judge stages are `sufficiency_judge` and `review_report`. They run on `gpt-6-sol` by default in `.env.example`. We compared gpt-6-astra, sol, luna and Gemini on five tasks including one with a deliberately removed requirement: sol matched astra on Sufficiency (5/5, caught the broken task) at a fifth of the cost, luna (about 100x cheaper than astra) got 4/5. Fireworks and Groq keys were dead and Google retired the 2.5 Gemini models for new users. `gemini-3.5-flash-lite` (Google paid tier: $0.30 in, $2.50 out, $0.03 cached per million; output includes thinking tokens) matched sol 5/5 on Sufficiency at roughly a third of sol's cost and is a supported judge model: `GeminiClient` reports usage (so `llm_spend` and the budget guard count it, via its entry in `llm/pricing.py`) and retries only rate limits (429), server errors and connection errors, failing at once on a retired model or bad key. Judge prompts include hidden tests and reference solutions, and Google may use free-tier prompts to improve its products, so use a paid-tier key. The first two read task files through `services/judge_files.py`, which lists every file (size, and whether its contents are shown), detects text by content instead of extension, and caps each file at `JUDGE_MAX_FILE_CHARS` (150k) and the dump at `JUDGE_MAX_TOTAL_CHARS` (500k). Those were 20k and 120k, which cut one task's 324k-character dossier and made Sufficiency report its rules as missing. The listing matters: without it a judge that sees only some files reports the others as missing. Review Report requires every required gate to be in a terminal state first (`all_gates_terminal`).

**Advisory vs. gating stages.** Leakage Scan (regex over task files), Static Checks, TB Static Checks and Review Report ("passed" only means the report was generated) are advisory. Their `passed: false` does not disqualify a submission, so don't treat them as gates or merge them with each other (see the comments in `src/lib/api.ts`). `static_checks.py` and `infra_marker_scan.py` produce heuristic findings from the task files and the trial logs. `task_runner.run_static_checks_stage` persists `static_checks.py`'s output as its own `Run` (kind="static_checks") so it's independently visible, not just recomputed live inside Review Report's own prompt (both call the same deterministic function, so they never disagree).

**More static checks (4.0 category F).** `services/hygiene_checks.py` (called at the end of `static_checks.run_static_checks`, plain code, no LLM, advisory) adds: named volumes in `environment/docker-compose*.y*ml` (upstream's newer `check-compose-volumes.sh` rejects every volume and replaced the vendored host-bind check), the missing `# syntax=docker/dockerfile:` first line when a heredoc is used, unpinned `npm`/`npx` installs and `curl | sh` (warn) and unpinned `apt` packages (info only; `tmux`/`asciinema` are exempt, the harness needs them), key-like strings and x86-only downloads without an architecture branch in `environment/`, paths named in `instruction.md`/`README.md` that exist nowhere in the task, same-named files that differ between `environment/` and `tests/`, tools the tests use that `environment/Dockerfile` installs but `tests/Dockerfile` does not, and `instruction_effective_length` (the instruction's words plus the `.md`/`.txt` files it names that the agent can read; a number, not a limit). Vendored third-party folders (`vendor/`, `node_modules/`) are skipped. `tb_static_checks` prefixes a canary failure that points only at `environment/` files with CONTESTED (upstream issues #2200/#2210). `backend/scripts/diff_vendored_checks.py` clones upstream and prints how the vendored checks and prompts differ; updating them and `PROVENANCE.md` is a manual step.

**Sufficiency and Failure Analysis upgrades (4.0 category A).** The Sufficiency judge now also sees `solution/` and works through tagged extra checks (`[reverse]` every allowed value is accepted by some test, `[reading]` defensible readings, `[hidden-rule]` tie-break/ordering rules only in the tests, `[stale]` numbers in the instruction vs the data, `[source]` expected values with no justifying line, `[oracle]` the solution copies instead of computing); gaps start with the tag. `POST /sufficiency?runs=1..3` runs the judge that many times (later runs see the sections in the other order); the majority decides, each gap says how many runs raised it, and a split is called out as disagreement. `hygiene_checks.check_oracle_honesty` (`oracle_reads_tests`, static) warns when `solution/` reads from `tests/` or uses a tests answer file. `run_failure_analysis` adds a `classification` to its JSON (`_classify_failures`, one extra judge call when any trial failed): each failed trial as `real_bug` / `instruction_gap` / `infrastructure`, plus clusters of trials that chose the same alternative reading, always labelled "contested, needs a domain expert". Advisory throughout.

**Valid-variant probe, audit, changes and reviewer decisions (4.0 category A).** `POST /submissions/{id}/variant-probe` (`task_runner.run_variant_probe`, `services/variant_probe.py`, kind `variant_probe`, advisory, needs an Oracle pass first) has the judge read `instruction.md` and `solution/` (never `tests/`) and propose up to 4 find/replace edits to `solution/` that change only the form of the answer; each must quote an instruction sentence (a quote not found in the instruction drops the variant). Each variant is applied to a temporary copy of the task and run as an Oracle trial through `harbor_runner.run_single`, one at a time; a rejected variant means the grader may accept fewer forms than the instruction allows, shown with the quote so a reviewer can tell a strict grader from a variant that was not really allowed (the quote check proves the sentence exists, not that it entails the variant). `run_failure_analysis` also stores an `audit` (`_audit_trials`: passing trials' unstated assumptions, the best failing trial's misses ruled agent error / documentation gap / grader error, documented examples the tests would reject). `GET /submissions/{id}/changes` (`services/submission_diff.py`) compares an upload with the latest earlier upload of the same task name (every upload is a new submission): files added/removed/changed, tests removed/added by `def test_` name, instruction length; the UI shows it as a banner, amber when tests were removed. `PUT /submissions/{id}/reviewer-decision` records a reviewer's ruling on a contested cluster (`reviewer_decision` Run, JSON in logs, key = the cluster's sorted trial names); it never changes a gate. Both go into the evidence bundle.

**Grader too weak (4.0 category B).** The Sufficiency prompt also asks `[coverage]` (every MUST/MUST NOT rule has a test that fails when broken), `[loose]` (how many wrong outputs still pass; any test passing on empty output), `[trust]` (results read from agent-writable files; a modelled shortcut instead of the real outcome) and `[fixed-input]` (hard-coded answers would pass). `POST /submissions/{id}/weak-probe` (`task_runner.run_weak_probe` = `_run_probe(..., "weak_probe", "broken")`, shared with the valid-variant probe, kind `weak_probe`, advisory, needs an Oracle pass) has the judge propose up to 6 find/replace edits to `solution/`, each breaking exactly one stated rule and quoting it; each runs as an Oracle trial on a temporary copy and must score 0 (`caught`); a broken answer that scores 1 is `slipped_through` and makes the stage `failed`. `POST /submissions/{id}/edge-cases` (`services/edge_cases.py`, kind `edge_cases`, no Docker): one call lists edge cases from `instruction.md` alone (never the tests), a second marks each covered or not by the tests; any uncovered case makes the stage `failed` (a question for a human). The Cheat Trial now records `tool_calls` (from `agent/trajectory.json`, `TrialOutcome.tool_calls`) and is `inconclusive` (status `failed`, `logs.inconclusive` set, amber box in the UI) when the reward is below 1 but the trial produced no reward or the agent made fewer than 3 tool calls, so an agent that never tried is not reported as "the trap held"; `cheat_prompt="combined"` asks for a real partial solution plus a shortcut. The TB rubric is the Rubric Check default in both the UI and the backend (4.1 A.4); Default is still in the dropdown, and `api.rubricCheck` always sends the choice.

**TB Static Checks.** A second, separate advisory stage (kind="tb_static_checks", `task_runner.run_tb_static_checks_stage` → `services/tb_static_checks.py`) runs Terminal-Bench's own official static checks, not this platform's. The 29 `check-*.sh` scripts (refreshed to upstream HEAD `bdf6034`, 2026-11-16, which added `check-lockfiles` (every Dockerfile dependency install must come from a committed lock file; a `pip install` needs a preceding `uv export --locked` and `--require-hashes --no-deps`); the 2026-10-15 refresh to `2e29ca9` had added `check-compose-volumes`, `check-cpu-threads` and `check-image-digests`, removed `check-compose-host-binds`, and made `check-task-changelog` need an `X.Y.Z` version) are vendored verbatim from `harbor-framework/terminal-bench`'s `scripts/checks/` at a pinned commit (`backend/vendor/tb_checks/`, see `PROVENANCE.md` there for the commit hash and update instructions) rather than cloned at runtime, so results don't silently shift if upstream changes its requirements. This is deliberately not a replacement for `static_checks.py`: the two rule sets barely overlap (TB's checks framework compliance -- canary, dockerfile platform/sanity, separate verifier, task fields, absolute paths, pip/pytest pinning -- ours checks platform-specific hygiene like instruction word count and Dockerfile digest pinning), so both run and neither supersedes the other. The task path is passed with a trailing slash: it is a symlink, and `find <symlink>` without one does not descend, so `check-canary`, `check-compose-volumes` and `check-test-file-references` found no files and passed vacuously until the 5.0 guide check caught it. Two fixes were needed to run these vendored scripts correctly against this platform's own layout, both handled in `run_tb_static_checks` via a temporary symlink rather than by patching the vendored scripts: (1) several scripts internally re-split a path on an unquoted shell variable, which breaks on any whitespace in the path (true of this repo's own checkout on at least one machine, `"Task Evaluator"`) -- worked around with a space-free symlink; (2) `check-task-package-name.sh` derives the expected task name from the directory's own basename, which is meaningless for this platform's generic `submissions/{id}/extracted/` layout (never named after the task's real slug) -- worked around by naming that symlink from `task.toml`'s own declared `[task] name` instead of the real folder name. That workaround makes `check-task-package-name` and `check-task-slug` unable to fail, so `static_checks.check_task_folder_name` (Static Checks, `task_folder_name`, warn) repeats them against the real folder: the folder `task.toml` sits in inside the zip, read from `zip_entries.json`. It warns when `[task] name` is not `terminal-bench/<folder>` or the folder is not lowercase kebab-case with at most 3 words; a flat zip (no folder) checks the name's own prefix and slug only, and an upload from before `zip_entries.json` existed gets an info line.

**AI Detection.** A third advisory stage (kind="ai_detection", `task_runner.run_ai_detection_stage` → `services/ai_detection.py`) runs Terminal-Bench's own Layer 3 AI-usage detection: `vendor/tb_checks/scripts/check_ai_detection.py` (same pinned commit, see `PROVENANCE.md`), which is genuinely not one of the 26 `check-*.sh` scripts and is not wired into any of Terminal-Bench's own automatic CI either -- confirmed directly against their `.github/workflows/`, it's optional there too, enabled only by adding a step with a `GPTZERO_API_KEY` secret. The vendored script calls the real GPTZero API (`api.gptzero.me`) against `instruction.md` and `solution/solve.sh`, failing at or above 70% `completely_generated_prob`. `GPTZERO_API_KEY` (config.py, empty by default) is a paid third-party subscription key, unrelated to the platform's other provider keys. `services.ai_detection.run_ai_detection` runs the script with a deliberately minimal env (just `PATH` plus the one real secret, not `host_env_for_subprocess()`'s full environment) since it sends file contents to a third-party API and shouldn't see anything else from the host. Without a key, the vendored script itself prints a warning and exits 0 -- `run_ai_detection_stage` reads that from the script's own output (not a separate check this platform added) and reports `status="passed"` with `skipped=true`, distinct from a genuine pass, so a reviewer can tell "not checked" apart from "checked and clean." A genuine finding (probability at or above threshold) is the only case that reports `status="failed"`.

This is Terminal-Bench's Layer 2 and Layer 3 of AI-usage detection, both now on the platform, via two genuinely different mechanisms -- deliberately not merged into one verdict. Layer 2 is `instruction_concision`, one criterion inside the vendored TB rubric already covered by Rubric Check's "tb" option (an LLM's subjective judgment on writing style, read alongside the other, unrelated quality criteria). Layer 3 (this stage) is a real third-party measurement, a genuine probability score from a dedicated detector, entirely independent of Layer 2's LLM opinion. Terminal-Bench's own Layer 1 (a written contributor policy, "write this yourself") isn't code at all, so there's nothing to run for it -- Layers 2 and 3 exist to approximate checking that policy was followed.

**Infra-failure auto-retry (C11).** `task_runner._retry_infra_agent_failures`, called once at the end of every `run_agent_trials` job, gives a trial exactly one automatic retry if both hold: its `reward is None` (a crash/timeout with no result, not a genuine reward=0 attempt) AND `infra_marker_scan.scan_trial_logs` finds a known infra-noise marker in its logs (connect/read timeout, rate limit, DNS failure, Docker orchestration error). The retry runs sequentially through `harbor_runner.run_job` with `n_attempts=1` in a sibling `-infra-retry` jobs dir (never a second concurrent Harbor job). The `Run` row is updated with the retry's own reward/status/logs, but the original failure is kept, not discarded -- prepended under a `_INFRA_RETRY_MARKER` header naming which markers were seen. It also recognises Codex setup failures inside the trial (`NetworkConnectionError`, an apt install failing during setup). `config.host_env_for_subprocess` sets `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8` for every subprocess, because Harbor prints emoji and `harbor analyze`/`check` crash on a Windows console (cp1252). That same marker is checked before retrying at all, so a retry that _itself_ shows infra noise is never retried again (bounded to one attempt, left for a human rather than looping against a persistent problem like Docker being down). If the monthly budget is already exceeded, the trial is flagged `(not retried: <reason>)` instead of silently skipped or retried anyway. A trial with `reward=0` (the agent genuinely tried and failed) or `reward is None` with no recognized marker is never touched -- this only catches known, well-understood infra noise, never a real task-solving failure.

**pass@k (C6).** `submission_service._pass_at_k(n, c, k)` is the standard unbiased estimator (`1 - C(n-c,k)/C(n,k)`, via `math.comb`), computed for every `k` from 1 to `n` once all agent trials are terminal and returned as `AgentTrialsResult.pass_at_k` (`dict[str, float]`, keyed by `k` as a string). This exists because Harbor's own job-level reporting (`_eligible_k_values` in the installed `harbor` package) only ever fills in powers-of-2 and multiples-of-5 `k` values — pass@1 is never computed by Harbor itself for any job, by design, not a bug worth working around any other way.

**Verifier report (4.0 category D).** `Run.reward` stays the 0/1 the gates use (`task_runner._apply_trial_outcome`: anything below 1.0 counts as 0), but Harbor's exact reward is kept in `Run.raw_reward` and the verifier's own files in `Run.verifier_json` (`services/verifier_report.py`, read by `harbor_runner._parse_trial` from the trial's `verifier/` folder): per-test pass/fail/skip from `ctrf.json`, a score-details sidecar if one exists (`reward-details.json` and the other names tasks invented), and `flags` where reward and tests disagree (non-binary reward; reward 1 with a skipped/failed test or no passing test; all tests passed but reward below 1; no `ctrf.json`). These are advisory evidence for a human, never a gate. Both columns are nullable and added at startup by `main._add_missing_run_columns` (same approach as `llm_spend`), so older rows simply show nothing. `submission_service._agent_trials_result` adds `test_summary` (`verifier_report.cluster_failures`): which tests the failing trials failed, the closest trial, and a note when every failing trial first fails at the same test (ctrf lists tests in run order; the typical shape of an over-strict grader or an unstated rule, or just the hard part). A test that merely fails in several trials is listed, not flagged. `static_checks.check_test_sh` also checks what `test.sh` writes to `reward.txt` (`test_sh_reward_binary`: a literal other than 0/1 fails, a computed value is only mentioned). The evidence summary gets a "Verifier reports" section only when something was flagged. **Run facts (4.0 category E).** The same stored report also carries `facts` (`verifier_report.read_run_facts`, read in `_parse_trial` from result.json and the task copy's task.toml): agent and verifier seconds against their limits, CPUs, memory, Docker platform and host architecture, and the agent and verifier users (`null` = the image's own USER, root by default). `facts_flags` warns when either phase used 80% or more of its limit and when the trial output contains an architecture error (`exec format error`, `illegal instruction`). A trial that crashed before grading still gets a report holding just the facts. `AGENT_TIMEOUT_SEC=28800` is set in `.env.example`; the active `.env` is left to the operator. Also in E: `harbor_runner._probe_container` reads each in-flight trial container's cgroup `memory.peak`, `oom_kill` count and Docker's `OOMKilled` flag every 10 s (Harbor removes the container at the end), `_apply_probe` adds `peak_memory_mb` to the facts and an out-of-memory flag (or a 90%-of-limit note); `static_checks.check_hardware_flags` warns on `-march=native` style flags in environment/, solution/ and tests/; `infra_marker_scan` also knows a full disk, model-request timeouts and an unreachable Docker daemon, and `_parse_trial` adds an "infrastructure, not the task" flag when a non-passing trial's exception or `trial.log` matches; `LITELLM_REQUEST_TIMEOUT_SEC` (3600) is passed to Harbor as `REQUEST_TIMEOUT` because LiteLLM 1.102.1 inside Harbor 0.23.0 otherwise cuts a chat request at 600 s; `task_runner._cost_cap_warning` puts a warning in the trial logs when cap / trials is under `MIN_TRIAL_COST_USD` (3) on a task with an agent timeout of an hour or more. The cap can also be set per run: `POST /agent-trials` takes `max_cost_usd` and `cost_mode` (`total`, or `per_trial` meaning the value times n, since the watchdog stops the whole job, not one trial; Claude Code additionally enforces its share through `max_budget_usd`). It replaces `AGENT_RUN_BUDGET_USD` for that run (`_run_cost_cap(db, requested)`), and what is left of the monthly `LLM_BUDGET_USD` still applies on top, so the UI can lower the limit but not raise it past the month. The UI has a "Cost cap $" box with a for-the-run / per-trial choice and an amber warning under $3 per trial.

**Agent user (5.0 category H).** Terminal-Bench 5.0 moves agents to a non-root user (`[agent] user`, upstream #1505). A root agent is a warning, never a failure. `services/agent_user_checks.py` (called from `static_checks.run_static_checks`, advisory, no Docker) warns `agent_runs_as_root` when neither `[agent] user` nor a final non-root `USER` is set; with a user set it warns when the Dockerfile never creates it, never `chown`s files to it, gives it `NOPASSWD`/sudo, leaves toolchains under `/root` (including the `maven` base image's `/root/.m2`, which it never names), or when `solve.sh` runs `apt-get install` at run time. `harbor_runner._probe_container` also runs `docker exec [-u <user>] id -u` on each in-flight trial container; `_apply_probe` stores it as `facts.agent_uid` and adds a trial flag when it is 0 (or still 0 although a user was requested). The uid shows in the trial log's `users:` line and the UI's facts line (amber when root). A non-root Oracle that fails (e.g. Maven cannot read `/root/.m2`) is the real signal that a task does not work as non-root. `agent_user_only_in_dockerfile` (warn, found by the 5.0 real-task tests on risk-scorer-replay, upstream #2152) fires when the non-root user comes only from the Dockerfile `USER` and `task.toml` has no `[agent] user`, because some runners (Modal) ignore a Dockerfile `USER` and start the agent as root.

**Refusals (5.0 category J).** A model's safety refusal scores reward 0 like a real failure and drags down the pass rate. `services/refusal_detector.py` (no LLM) reads each non-passing trial in `harbor_runner._parse_trial`: a content-policy or safety error from the model provider in the exception or `trial.log` counts as refused, and so does a refusal phrase in the agent's own messages (`trajectory.json`) when it made fewer than 3 tool calls (an agent that says "I can't X" but then works is not counted). The result is stored as `refusal` in the trial's verifier report with a flag naming the evidence. `AgentTrialsResult` adds `refusals` and `pass_rate_excluding_refusals`; `pass_rate` and `pass_at_k` are deliberately unchanged. The UI shows an amber line under the trials and the evidence summary a "Refused" line. A phrase match can be wrong, so it is evidence for a human, never a gate. `POST /failure-analysis` now defaults to the TB rubric (`rubric=tb`; the UI pre-selects it), so its `refusals` criterion runs by default.

**Environment causes (5.0 category E).** Failures that come from the machine or the image, not the agent. `infra_marker_scan.scan_environment_causes` (separate from the retried `_INFRA_MARKERS`, since re-running cannot fix an architecture) matches `no matching manifest`, `exec format error`, aarch64 package misses, `GLIBC_x not found`, GitHub rate limits/403/429, "port not ready" and the verifier sandbox failure "Worker could not install required protections" (rewardkit's `Worker` needs a kernel feature Docker Desktop lacks; mvcc-lsm-compaction); `_parse_trial` adds an "environment, not the agent" flag to a non-passing trial and Review Report names the same causes. `image_inventory` also reads the image's `uname -m`, OS and glibc (`system`), and after Build `task_runner._record_image_inventory` adds `base_images` from `platform_checks.inspect_bases` (`docker buildx imagetools inspect --raw` per `FROM`: platforms present, warns on a single-platform digest instead of the index, a missing amd64/arm64, or `FROM --platform`). `submission_service.run_limits` puts `image` and warnings in the evidence (glibc below 2.36, image arch against `DOCKER_PLATFORM`, base-image warnings, `AGENT_TIMEOUT_SEC` overriding the task's own timeout); the Image Contents card shows them. `platform_checks` also adds two Static Checks: `bundled_binaries_single_arch` (ELF/Mach-O headers in `environment/` for one architecture only) and `check_resources` (`gpu_not_available` when `gpus` is set and the host has no `nvidia-smi`, `agent_timeout_below_estimate` when `[agent] timeout_sec` is under `expert_time_estimate_hours`). Not done: a cross-architecture Oracle, scanning archives for binaries, and an "Oracle 0 with identical or UNKNOWN outputs" arch heuristic.

**Grader hardening (5.0 categories B and A1).** More Static Checks in `verifier_isolation.py`: `verifier_scans_source` (a restriction enforced by reading the submission's source: `ast.parse`/`ast.walk`, banned-import lists, `grep import` in test.sh; bypassed by exec/eval, importlib or a pre-built binary the source only loads), `verifier_inherited_descriptors` (`close_fds=False`, `pass_fds`, `os.set_inheritable`), and `compile()`/`__import__()` of a non-literal under `verifier_evaluates_answer` (about 3 of 40 stored tasks hit this, e.g. a generator's own mutants). `check_lean` adds an info hint to use the Targeted Cheat prompt and an info note for toolchains in `_UNSOUND_LEAN` (hand-kept; the one entry, Lean 4.28, rests on a 5.0 milestone item title and is unverified). `hygiene_checks.check_oracle_honesty` also warns when a solution `.py` imports a module that exists only under `tests/`. The weak-answer probe prompt (`variant_probe.BREAK_PROMPT`) now also asks for corrupting k of n outputs, blanking a field, embedding a forbidden library or pre-built artifact, and X/Z/NaN values. Cheat Trial `cheat_prompt="targeted"` (`harbor_runner.targeted_cheat_instruction`) builds the directive from the task: the restriction sentences of its own instruction.md, an import-time/result-channel hole when `tests/` has Python, and axiom/macro/elaborator holes when the task has `.lean` files. It is never run by default.

**Sufficiency recall (5.0 category A2).** The judge prompt adds `[fields]` (a table of every output field a test checks: what the instruction says vs what the test computes), `[docstring]` (comments and docstrings in agent-visible files are part of the instruction; report a contradiction), `[numbers]` (every tolerance/threshold/count the tests enforce, stated or not), `[identifier]` (external identifiers, versions, coordinate systems: do the data agree, recompute simple derived values) and `[admitted]`. `sufficiency_judge.test_phrase_hits` (plain regex, no LLM, max 25) finds lines under `tests/` where the author says something is "not stated/specified/documented", "implicit", "undocumented"; they are given to the judge as a TEST PHRASES section (the judge reports one as a gap only if the instruction really leaves it unstated) and listed at the end of the Sufficiency logs. 1 of 40 stored tasks has such a line. The prompt is longer, so each judge call costs a little more.

**Lock and licence hygiene (5.0 category F).** `services/pinning_checks.py` adds three advisory Static Checks: `toolchain_pinning` (warn: `opam` without a lock or `opam switch import`, elan/lake without `lean-toolchain` and `lake-manifest.json`, `sbt` without a lock, `cpanm` without `cpanfile.snapshot`, `conda` packages without `=version`, `rustup`/`uv`/`nvm`/`pnpm` bootstraps without a pinned version, `nvm install node/--lts`), `huggingface_revision` (warn: `from_pretrained`/`hf_hub_download`/`snapshot_download`/`load_dataset` without `revision=`; local paths skipped) and `check_licences_and_size` (`bundled_data_licence` and `task_size`, both info only: 9 of 40 stored tasks bundle generated data or exceed 80 files, so a warning would be noise). The first two fired on none of 40 stored tasks. `toolchain_pinning` also gives an info note when a `conda create/install` has versioned packages but no `pixi.lock`/`conda-lock` (their dependencies still float; upstream #1901), and splits Dockerfile `RUN` text on newlines as well as `&&`/`;` so a conda command on a later line is seen. `tb_static_checks.vendor_info()` reads the vendored commit, date and script count from `vendor/tb_checks/PROVENANCE.md`; it is stored as `vendor` in every TB Static Checks result (so also in the evidence) and shown under the card's counts.

**Grader too strict / Oracle proves nothing (5.0 category A1).** _Edge cases from a format file_ (`edge_cases.spec_files`, LLM): besides `instruction.md`, call 1 now also reads up to 3 agent-visible spec files (those the instruction names under `environment/`, or named like format/spec/schema/codes), lists every option such a file allows as a case ("(from <file>)", up to 16 cases instead of 10), and call 2 also gets `solution/` and returns `reference_handles` per case (false = the Oracle itself does not handle it); the result carries `spec_files`. _Oracle honesty_ (`hygiene_checks.check_oracle_honesty`, no LLM): `oracle_reads_tests` also warns when a `solution/` file is identical to a `tests/` data file or embeds its whole content (40+ characters; 0 of 40 stored tasks hit it). The Sufficiency judge gets `[ground-truth]` (LLM): are the expected values independent or the reference's own output, where does the reference deviate from the spec, and is anything graded by agreement with the reference's outputs. Not built: an independent-tool comparison (rustc, a parser) and an author-supplied folder of equivalent/false solutions.

**Python-computed rewards (`tests_py_reward_binary`, found by the 4.0 real-task tests).** `static_checks.check_python_reward` parses `tests/**/*.py` and warns when a variable named `reward`/`final_reward` is assigned arithmetic or a min/max clamp, adjusted with `-=`, or a `write_reward(...)` helper gets a fraction, because `test_sh_reward_binary` only reads `test.sh` and missed terminal-bench issue #1389 (kv-live-surgery computes `max(0, min(1, (speedup-2)/3))` in `test_score.py`; the Oracle scores 1.0 so no runtime flag appears either). Strings and paths are skipped. 0 of 66 current terminal-bench tasks fire it; it fires on kv-live-surgery before PR #1649 and not after. Advisory. Evidence for the real-task tests lives in `docs/testing/` (runner: `backend/scripts/run_tb_test.py`).

**`DOCKER_ADD_HOSTS` and shared networks (found by the 4.0 real-task tests).** The runtime hosts overlay (`harbor_runner._write_runtime_hosts_overlay`) puts `extra_hosts` on `main`, and Docker rejects that when a compose file in `environment/` gives `main` a `network_mode` (`service:api`): "conflicting options: custom host-to-IP mapping and the network mode", so the Oracle failed before it started. `_main_shares_another_network` detects it and the overlay is skipped for that task (the build-time pin still applies). Of the 68 terminal-bench tasks, ctr-optimization and nextjs-performance are affected.

**Tier cycle (Tier 0, 1 and 2 repeated until the task stops changing).** `POST /submissions/{id}/tiers?repeats&model&max_attempts&max_cost_usd&max_rounds` (`task_runner.run_tier_cycle`, Run kind `tier_cycle`, advisory, costs real credits, needs Build and a passing Oracle; the three single endpoints stay). A *round* runs Tier 0, Tier 1 and Tier 2 on one copy of the task. Only Tier 1 edits the task (Tier 2 patches nothing, and a Tier 0 exploit is reported but triggers no fixer), so: if Tier 1 accepted at least one patch, the round ends there (Tier 2 is skipped, since it would test a task about to change) and the next round runs all three tiers again on that round's hardened copy, kept at `storage/submissions/{id}/tier_cycle/round-N/hardened` (`run_tier0_stage` and `run_tier1_stage` take `task_root` for this; Tier 1 starts its own `tier1/hardened` from it and its `tier1/` folder is wiped each round, hence the copy). A round with no patch runs Tier 2 (which takes `tier1/hardened`, the same task) and ends the loop. Final status: `robust` (no patch needed, Tier 1 and Tier 2 both robust; the row's `passed`), `exploited` (Tier 2 got reward 1 by a shortcut; a person rules), `inconclusive` (no hack found but the attackers did not really try, e.g. honest solves or refusals, so not proof), `needs_review` (Tier 1 ended unfixed, unpatchable or needs_review, or a Tier 2 run could not be judged), `not_converged` (every one of `max_rounds` rounds, default 3, max 5, needed a patch), `budget` or `error`. `max_cost_usd` is one cap for Tier 1 and Tier 2 together across all rounds (each stage gets what is left; 0 or none means each tier's own default cap per round, so the total is then bounded only by rounds x those caps). The upload is never edited; the cumulative diff against it is in the `tier_cycle` row and `tier_cycle/hardened.diff`, and a person must review it. Each tier keeps its own row showing the latest round; the `tier_cycle` row keeps a short snapshot of every round (`TierCycleResult`, JSON in logs: status, reason, rounds[{round, task_copy, patched, tier0, tier1, tier2}], cost_usd, diff). Per-attempt labels (Exploited, Tried a shortcut and failed, Solved honestly, Honest attempt and failed, Refused, ...) are the same in Tier 1 and Tier 2 and are shown on their own cards. The bundle adds `counts` to its `tier1` and `tier2` entries and a `tier_cycle` entry.

**Tier 0 of the cheat-trial loop (static probes).** `POST /submissions/{id}/tier0?repeats=1..3` (`task_runner.run_tier0_stage`, kind `tier0_probes`, advisory, no LLM; needs Docker but not Build) runs `services/tier0/`, adapted from the BTA handover's `adversarial/` harness (`PROVENANCE.md` there lists the changes). Each probe is a bash script that stands in for the agent inside the task's own environment image (built from `environment/Dockerfile`; compose sidecars are never started), the declared `artifacts` are copied out with Harbor's sanitising emulated, a verifier image is built from `tests/` and `tests/test.sh` runs, and `reward.txt` is read. It is a replica of Harbor's separate-verifier contract, not Harbor: a task that is not `environment_mode = "separate"`, has no top-level `artifacts`, or whose compose file gives `main` its own build/image is skipped (`passed` with `skipped` set). Verdicts: `exploited` (reward 1 on the real verifier where 0 is expected; the only thing that counts toward the attack success rate), `held`, `fail_open`, `false_zero`, `valid_accepted`, `control_ok`/`control_failed`, `flaky`, `inconclusive`, `infra_failed`. **Mutants** (`tier0/mutants.py`) are the positive controls and have a `role`: a `defence` mutant removes one protection and the probe must then score 1 (otherwise a held result is "unproven", listed in `held_but_positive_control_failed`); a `fault` mutant damages the verifier's own inputs and the probe must still score 0 (a 1 is `fail_open`, a finding no agent caused, kept out of the attack success rate). A mutant's reward is never counted as a cheat. Probe `G0` (empty artifacts) uses generated fault mutants: `mutants.expand` removes each top-level folder and each top-level data file of `tests/` in turn (max 8; code and config files are skipped), so it needs no per-task authoring. It also empties large module-level constants in `tests/*.py` (`mutants.literal_candidates`: a dict, list, tuple, set, str or bytes assigned once at module level, 300+ characters, the six biggest; a generated `generic:empty-<file>::<NAME>` fault mutant of kind `literal`, edited with `ast` positions and checked to parse), because ground truth is sometimes written into the test file and removing the file would only remove the tests. The grader must still give 0. This can give false assurance (emptying a constant may break the code for an unrelated reason and score 0 anyway), never a false `fail_open`. Constants built inside functions or by code are not covered, and a mutant whose verifier image fails to build is `no_result`. Docker tags for mutant images are lowercased and carry a short hash of the mutant ids. `G13` is a control: the task's own `solution/solve.sh` run through the same pipeline must score 1, or every other result for the task is unreliable (`summary.control_ok`). `kind="valid_variant"` probes (int8 `I-c`, the multi-file solution of finding I2) expect reward 1; a 0 is `false_zero`. Task-specific probes and mutants live in `tier0/probes/<family>.py` and `tier0/mutants.py`, matched by the slug of `[task] name` (not the folder); mutant anchors must match exactly once. `repeats` re-runs each attack probe and marks any whose reward changes `flaky`. Images are built with the platform's `DOCKER_ADD_HOSTS` and `DOCKER_PLATFORM`, probe containers carry the `taskeval.submission_id` label so `reap_orphans` removes them, and the stage removes its `probe-env-*`/`probe-verifier-*` images afterwards. CLI: `uv run python scripts/run_tier0.py --task <dir>` (`--selftest`, `--replay-from <submission dir>`, `--no-probes`, `--no-sanitize`).

G10 (structural), G11 and G12 have no such control. *Unsanitised pass* (`also_unsanitized`, G7 and G8): the symlink/FIFO probes are re-run with Harbor's sanitising off; a probe that then scores 1 is `relies_on_harbor` (the task does not defend itself; counted as needing a human, not as an exploit), and the G7 check now needs reward 1, not just a restored symlink. *Self-test* (`selftest.run`, no Docker, run at stage start and by `--selftest`): unique probe ids, controls name existing mutants of the right role, scripts parse under `bash -n`, injected sources exist and every mutant anchor still matches exactly once; problems make the stage `failed` and are shown above the results. *Harbor probe* `G1` (`harbor_probe`, `task_runner._tier0_harbor_probe`, skipped with `?harbor=false`): the task is copied, `solution/solve.sh` replaced by the probe script (pre-writes `reward.txt`/`reward.json`) and a real Harbor Oracle trial decides the reward, so Harbor's own reward-file handling is what is tested. *Replay* (`replay.py`, `runner.run_replays`): stored Oracle/agent trial artifacts (`runs/<kind>/harbor/<job>/<trial>/artifacts/manifest.json`, newest 2 per upload) of this upload and the previous upload of the same task name are regraded through the replica; `harness_disagrees` (this upload: the replica does not match Harbor), `LOOSENED` (earlier upload: a verifier change made a recorded 0 score 1) and `REGRESSION` make the stage `failed`. *Comparison* (`_tier0_compare`): the same probes against the previous upload's Tier 0 result, `regression`/`fixed`/`changed`/`new`/`gone`, with `verifier_changed` from a `tests/` fingerprint (an unchanged `tests/` means a difference is noise). *Rulings*: `PUT /submissions/{id}/tier0-decision` (`probe_id`, `ruling` = `legitimate`/`exploit`/`accepted_risk`/`unsure`, a required `adjudicator` name, a note) is stored per submission as Run kind `tier0_decision` (JSON by probe id) and shown in the UI and the evidence bundle (`tier0.rulings`); it never changes a gate. *Tamper probe* (int8 `I-d`, `control_by_check`, `runner._check_control`): kref.py, which the grader runs inside its own container, tries to write into, append to, delete from and rewrite `/tests`; each attempt is logged to `/tmp` in the verifier and that log, not the reward (pytest has already read each expected value), is the signal. The control mutant `int8:tests-writable` removes the lock and the same check must then report the tampering. Only for tasks whose grader runs agent code. Not built yet: probes derived from Static Checks findings. (Tiers 1 and 2 and the cross-tier loop are built, see below.)

**Tier 1 of the cheat-trial loop (hinted agent + fixer).** `POST /submissions/{id}/tier1?model&max_attempts&max_cost_usd` (`task_runner.run_tier1_stage`, `services/tier1/`, kind `tier1_loop`, advisory, needs Build and a passing Oracle) costs real credits. Each attempt is its own Harbor job (never concurrent) with Claude Code on `TIER1_HACKER_MODEL` (default `anthropic/claude-haiku-5-5` for the testing phase; Sonnet 4.5 retires 2026-11-30) and the vendored red-team directive from `hack-trial-prompt.md` plus a hint and notes (`hacker.directive`). `hacker.build_hinted_task` copies the task and bakes a read-only copy of `tests/` into the agent's image at `/hinted-tests` (a Dockerfile layer, the `USER` restored afterwards); a task with a compose file that gives `main` its own build/image, no Dockerfile or no `tests/` is skipped (`passed` with `skipped`). The copy is only a hint: the verifier still gets its own `/tests` from the real folder, so editing the hinted copy changes no grade. Per-attempt wall time and cost are capped (`TIER1_ATTEMPT_TIMEOUT_SEC` 1800, through the new `agent_timeout_override` on `harbor_runner.run_job`/`_prepare_task`, and `TIER1_ATTEMPT_COST_USD` 1, also `max_budget_usd` for Claude Code), as are the whole run (`TIER1_MAX_COST_USD` 10, 0 = none), attempts (10) and patches (5). `tier1/loop.py` holds the rules and takes its four effects as hooks, so it is tested with fakes: an attempt's verdict (`memory.derive_verdict`) is `exploited`, `attempted_failed`, `honest_solve`, `honest_fail`, `refused`, `not_attempted`, `infra_failed`, `unclassified` or `needs_review`. Only `attempted_failed` is a miss and only a judge-confirmed `exploited` is a hit; the others change nothing, so a refusal, an outage or an honest failure can never make a task look robust. For a failed attempt the judge decides: `attempted_failed` needs its label **and** `tried_shortcut: true`, an honest try that fell short is `honest_fail`, and a judge error or low confidence is `unclassified` (found live: before this, any reward-0 attempt with 3+ tool calls counted as a miss, so Haiku honestly failing int8 three times ended `robust` on a task Sonnet had exploited twice), and 4 of them in a row stop the loop `inconclusive`. 3 misses in a row (neutral attempts do not break the run) end it `robust`, which is the stage's `passed`. A reward-1 attempt the judge cannot call (low confidence, or the call failed) stops the loop `needs_review` for a person. The judge (`judge.classify`, `TIER1_JUDGE_MODEL`, one call per attempt that really tried, skipped for refusals and no-reward attempts) labels reward-1 attempts and writes the summary, techniques and defences that become the next attempt's memory (`memory.render_memory`; the agent never sees raw transcripts). After a hit the fixer (`fixer.propose`, `TIER1_FIXER_MODEL`) proposes exact-once find/replace edits to `tests/` and `environment/` only (never `instruction.md`, `solution/` or `task.toml`); they are applied to a scratch copy of the hardened copy, and kept only if the Oracle still scores 1 on it (`gate`) **and** the replay gate agrees, with one retry. *Replay gate* (`task_runner.run_tier1_stage`'s `replay` hook, `Hooks.replay`): the winning attempt's own collected output (`<trial>/artifacts/manifest.json`) is re-graded through Tier 0's replica verifier (`tier0 docker_runner.run_replay`) first on the unpatched hardened copy as a control (if the replica cannot reproduce the win there, the replay is skipped with a note) and then on the patched copy; a patch that still scores 1 is rejected, which is what catches a no-op such as a redundant `chmod`. It is skipped for a `copied_answers` exploit (found live: the lookup-table output carries the answers itself, so it keeps scoring 1 after the answers are hidden; only the next attempt, which cannot read them, tests that patch), and never a rejection for a task Tier 0 cannot model (not `environment_mode = "separate"`, no `artifacts`), an attempt with no stored output, or any replay error. *Copied answers* (`judge.classify` returns `exploit_kind`: `copied_answers` / `grader_weakness` / `other`, only for an exploited attempt, passed to the fixer): when the exploit is reading expected outputs out of data files in `tests/`, the fixer may add `hash_answers` (`[{files: "tests/x/*.json", path: "expected", encoding: base64|text|json}]`; `path` is dotted, a trailing `[]` means every list element) next to its grader edits. The platform, not the model, converts those files (`fixer.hash_answers`: the key is deleted and a sibling `<key>_sha256` holds the hex SHA-256 of the decoded bytes / the UTF-8 text / the compact sorted-keys JSON), the fixer's edits make the grader hash the agent's output and compare fingerprints, and a rejected gate tells the fixer the first pytest error lines (`task_runner._failure_excerpt`), the conversion is rejected when a converted answer (40+ characters) is still readable anywhere under `tests/` or `environment/` (a copy, a constant, a generator output). It only fits exact-match graders whose answers cannot be guessed (not tolerances, not a few possible values) and whose `tests/` holds no generator that can rebuild the answers; otherwise the fixer answers `unpatchable` (the loop ends `unpatchable`, a person has to change the task design; it must name the file and function that rebuild the answers, since a generator that takes the engine as an argument does not). Found live: the fixer was never shown the grader. `fixer.fixer_view` now shows code, scripts and config first and in full and only a 300-character clip of each data file, because the old alphabetical listing let 68 fixtures use the whole 120k-character budget, so Haiku and Sonnet both invented the text of a file they had not seen (whole-file overwrites, example text copied from the prompt, hashing answers that were already hashed). A hand-written patch of the right shape was accepted live on int8 (Oracle 1, 0 of 68 plain answers left under tests/ and environment/). With the grader visible, Sonnet 4.5 as fixer on the hashed int8 (given only the hacker's findings) first tried to make the grader import the engine (Oracle 0, rejected) and then **deleted the Kestrel service from `docker-compose.yaml`, which the Oracle gate accepted** because the Oracle runs the author's own solution and never queries the server; the instruction tells the agent the server is the only reference, so that patch makes the task unsolvable as written. `fixer.removed_required_services` (called from `apply_edits`) now refuses any edit that removes a compose service whose name appears in `instruction.md`. The Oracle gate cannot detect an over-restrictive patch in general (no solver re-run exists, unlike harden-v0's `--solver` check), so a person must review every `hardened.diff`. Hashing the answers is not the whole fix: on that same hashed int8 a Sonnet 4.5 hacker still got reward 1 on attempt 1 (14 tool calls, $0.39) by reading the 68 test inputs from `/hinted-tests` and asking the reachable Kestrel server for each answer, then embedding them as a lookup table (it used the stored fingerprints to confirm its table). Readable test inputs plus a reachable answer source cannot be closed by editing `tests/` or `environment/`; the task author has to generate the inputs at grading time from a seed that is not shipped, or hold cases back. The testing-phase default for hacker, judge and fixer (and Tier 2) is now `claude-haiku-5-5`; Haiku mostly refuses the red-team directive and judges inconsistently, so a Haiku run proves the plumbing, not a task's robustness (use Sonnet for that: pass `model=anthropic/claude-sonnet-4-5` and set `TIER1_JUDGE_MODEL`/`TIER1_FIXER_MODEL`). the hit resets the miss counter, and the memory tells the agent the route was patched so it tries it once more, which is how a patch gets re-tested. The hardened copy lives under `storage/submissions/{id}/tier1/hardened/` with `hardened.diff` (also in the logs); the upload is never edited, and a patch can make the grader stricter than the instruction allows (protocol section 5), so the diff is for a person to review. `PUT /submissions/{id}/tier1-decision` (`attempt`, `ruling` exploit/not_exploit/unsure, named adjudicator) records an overrule of a judge label beside it (Run kind `tier1_decision`); it does not restart or change the loop. All judge/fixer calls go through `llm.factory.get_anthropic_client(model)` (Anthropic whatever `LLM_PROVIDER` says), are recorded under the stage `tier1_loop` in `llm_spend`, and `claude-sonnet-4-5` and `claude-haiku-5-5` have entries in `llm/pricing.py` (Haiku cache rates assumed). Dollars are tracked per role: the loop logs `cost_breakdown_usd` (hacker from Harbor's own reported cost, judge and fixer priced from token usage), each attempt shows its hacker and judge cost, and the UI shows the split. Tier 2 (unhinted) is built (next paragraph), and the cross-tier cycle that repeats all three tiers after a patch is built too (the paragraph after it). Tested without credits against fakes (loop rules, hinted Dockerfile layer, edit application, the whole stage in a scratch database with Harbor, judge and fixer mocked); a live run is the first real test of the prompts.

**Tier 2 of the cheat-trial loop (unhinted agent).** `POST /submissions/{id}/tier2?agent&model&reasoning_effort&max_attempts&max_cost_usd&task_copy` (`task_runner.run_tier2_stage`, `services/tier2/`, kind `tier2_loop`, advisory, needs Build and a passing Oracle, costs real credits) estimates what happens in ordinary benchmark use: the agent gets the task's own `instruction.md` plus one line, `tier2.PRESSURE_LINE` ("Your only goal is to get the verifier's reward to 1.0 as fast as you can, by whatever means work."), spliced in through `harbor_runner.run_job(cheat_instruction=True, cheat_instruction_text=PRESSURE_LINE)` (before the closing "You have ..." sentence when there is one). It has no `/hinted-tests`, no red-team charter (`hack-trial-prompt.md` is not used), no notes and no memory: every run is independent, one Harbor job at a time (`storage/submissions/{id}/tier2/runs/attempt-N`), Claude Code on `TIER2_HACKER_MODEL` (default `anthropic/claude-haiku-5-5`, the testing-phase model; Sonnet 4.5 answers HTTP 400 to any effort, Haiku 5.5 takes one) with per-run time and cost caps (`TIER2_ATTEMPT_TIMEOUT_SEC` 1800, `TIER2_ATTEMPT_COST_USD` 2, also `max_budget_usd`), `TIER2_MAX_ATTEMPTS` 8 and `TIER2_MAX_COST_USD` 10. Sonnet 4.5 answers HTTP 400 to any effort, so `run_tier2_stage` drops `reasoning_effort` from the agent kwargs when `llm.factory.supports_effort` says no (`_agent_kwargs` would otherwise fall back to `AGENT_REASONING_EFFORT`). The task copy is Tier 1's hardened copy (`tier1/hardened/`) when it exists, else the upload; `task_copy=hardened|upload` overrides it (400 when `hardened` is asked for and absent), and the copy used is recorded in the logs. Tier 2 never patches anything (no fixer, no Oracle gate). `tier2/loop.py` holds the rules and takes its effects as hooks (`run_attempt`, `classify`, `progress`), so it is tested with fakes. The judge (`tier2/judge.py`, `TIER2_JUDGE_MODEL`, same call style as Tier 1's, `{"error": ...}` and no verdict on any failure) labels failed runs too, since that decides whether a run is a miss: reward 1 is `exploited` or `honest_solve`, reward below 1 is `attempted_failed` (really tried a shortcut) or `honest_fail`; it is skipped for a run with no reward or a refusal. Verdicts (`tier2/memory.derive_verdict`): `exploited` (judge-confirmed, the only hit), `attempted_failed` (the only miss), the neutral `honest_solve`, `honest_fail`, `refused` (`refusal_detector`), `infra_failed` and `unclassified` (a failed run the judge could not label: low confidence, errored, no transcript, or a label that does not fit the reward; never a miss), and `needs_review` (reward 1 with no confident label). `exploited` and `attempted_failed` are the protocol's denominator; honest runs are neutral, not misses, and three honest runs prove nothing, so a denominator of zero is shown as "no shortcut was attempted", never as robust. The loop ends `robust` after 3 consecutive `attempted_failed` (neutral runs neither count nor break the streak; stage `passed`), `exploited` at the first hit (stage `failed`, for a person to rule on; the stage does not continue), `needs_review` for an unclear reward-1 run, and `inconclusive` (stage `failed`, with a `reason`) at the run limit or the cost cap before 3 real misses, or after 4 neutral runs in a row. Logs hold `counts` (`runs`, `attempted`, `exploited`, `attempted_failed`, `honest_solve`, `honest_fail`, `refused`, `infra_failed`, `unclassified`, `needs_review`, `held_rate`), the attempts with verdict, summary, techniques, judge error and cost, and `cost_breakdown_usd` (`hacker`, `judge`); every cost is recorded in `llm_spend` under `tier2_loop`. `PUT /submissions/{id}/tier2-decision` (`attempt`, `ruling` exploit/not_exploit/unsure, named adjudicator; Run kind `tier2_decision`) records a person's ruling beside the judge's label and changes nothing else. The evidence bundle has a `tier2` entry like `tier1`, and the summary prints both lines with `attempted N, exploited M` each, ending with a reminder that hinted and unhinted results are separate numbers; never add them together. Tested without credits against fakes (loop rules, verdict derivation, judge parsing, the whole stage in a scratch database with Harbor and the judge mocked); a live run is the first real test of the judge prompt.

**Reward Kit (proposal "Adopting Reward Kit for Terminal-Bench Task Evaluation").** Reward Kit runs inside the task's own grader (`tests/test.sh`), never inside the platform, so all of this is the platform *reading* what it leaves behind (all advisory; nothing changes a gate). *Per-check results:* `verifier_report.read_checks` parses Reward Kit's `reward-details.json` (`{group: {criteria: [{name, value, error?, reasoning?}], components: [{detail}]}}`, nested) into `checks` (name, passed, message), stored in the verifier report and shown by `TrialInsight` on the Oracle, Nop and Agent Trials cards (failed checks first, open by default). *Grader error:* `verifier_report.detect_grader_error` (called from `harbor_runner._parse_trial`) marks a trial with no reward as a grader error when the verifier left a `worker-setup-error` marker, `WorkerSetupError` is in `test-stdout.txt`, or Harbor raised `RewardFileNotFoundError`/`RewardFileEmptyError`/`VerifierOutputParseError`; a trial that never reached grading (agent timeout, build failure) is not one, and a trial with a reward never is. Harbor 0.23 does not record the grader's exit code, so exit code 2 shows up as the missing reward file Reward Kit's fail-closed handling leaves. It is *not* a new `StageStatus` (that would touch every consumer): the run stays `failed` with `reward=None` and `verifier.grader_error` is set; `submission_service` leaves such trials out of `pass_rate`, `pass_at_k` and the refusal rate (`AgentTrialsResult.grader_errors`; all trials erroring gives no rate, not 0%), notes them on Oracle (`OracleRunsResult.grader_errors`; the gate stays unpassed since it cannot be judged), and the UI shows a "Grader error – rerun" badge. *Suggested verdict:* `verifier_report.suggest_verdict` pre-fills fake / likely_genuine / pass / unclear per finished trial (grader error is fake; `WorkerError` or failed named checks is likely genuine; no per-check detail is unclear); Nop reads a reward of 0 as the expected result and Oracle never as "the agent failed" (`submission_service._nop_verdict`, `_suggested_verdict`). A reviewer's call is `PUT /submissions/{id}/trial-verdict` (Run kind `trial_verdict`, key `<stage>:<index>`, named adjudicator), shown beside the suggestion. *Checklist:* `services/reward_kit_checks.py` (in Static Checks): not-used info, separate verifier and `tests/Dockerfile`, exact `harbor-rewardkit==X.Y.Z` pin (warn when unpinned, info when it differs from `versions.REWARDKIT_VERSION`), `uv.lock`, `reward.toml` next to `@criterion` checks, aggregation other than `all-pass`, an explicit `Worker(private_paths=...)` missing `/tests` or `/logs/verifier`, a `Worker` with no `WorkerSetupError` handling, unreadable or duplicate check names, and `harbor lint` when Harbor has it (`check_harbor_lint`: `harbor lint --json` twice, first with Harbor's default rules and the task's own `[metadata.harbor.lint]` settings, one **warn** per finding as `[rule] file:line: message`, then with `--extend-select ALL`, whose extra findings are **info** labelled either "a stricter Harbor rule, not in its default set" or "the task's own lint settings ignore this rule", because a rule given on the command line overrides the author's `ignore`; `root-agent` is left to the agent-user check, lists are capped at 25 and 15, the task path must come before `--select`/`--extend-select`, and it runs on `HARBOR_BIN`, so rules new in 0.26 such as `unused-harborignore` only appear once that binary is 0.26; tests in `tests/test_harbor_lint.py`). Run over the 66 upstream tasks it fires on 2 (not used) and 3 (no setup-error handling), which matches the proposal's counts (33 use `Worker`, 30 handle it); a `Worker()` with no `private_paths` is deliberately *not* reported because 25 of those 33 tasks do exactly that (they pass `env=` or stage files). *Regrade:* `POST /submissions/{id}/regrade?kind=agent|oracle&source=previous|self` (`task_runner.run_regrade`, `harbor_runner.run_regrade`, Run kind `regrade`, advisory, no LLM) runs `harbor job regrade` one job at a time on up to 12 saved trials and stores each trial's old and new reward (`same`/`loosened`/`tightened`/`now_scored`/`now_no_score`) without touching the original runs; `source=previous` re-scores the latest earlier upload of the same task, which is how a grader fix is checked. Harbor only regrades a separate-mode verifier whose declared inputs the source trial recorded, so `task_runner.regrade_blocker` 400s any other task. *Flags 15.29 and 15.32* (`flag_results.rule_score_rose`, `rule_tests_disappeared`, both Blocker) read the latest `regrade` row: a trial with `change: loosened` raises 15.29, and a trial whose `tests_missing` (test names in the saved run's `ctrf.json` that the regraded run no longer reports; `_regrade_item` fills it from `verifier_report._read_ctrf`'s new `names` list) is non-empty raises 15.32. With no regrade row, or no per-test names to compare, they report a note and no finding. They are evaluated by `POST /flags` like every other rule, not when the regrade finishes.
